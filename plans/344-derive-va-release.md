# Plan: derive `va_release` in the discogs-cache (#344)

## Problem

The compilation-track recall-index build (LML's `scripts/build_compilation_track_location.py`, wired into `sync-library.sh` daily and `rebuild-cache.yml` monthly by #339/#340) crashes against the prod discogs-cache with `UndefinedTableError: relation "va_release" does not exist`. The table was an ad-hoc artifact of the VA-disambiguation project that only ever existed on a local dev DB; it was never part of this repo's schema. Until it exists in prod, the daily incremental build soft-fails every run and the LML#1027 full build (which gates LML#1026's prod promotion) is dead on arrival.

## Approach (Option A from the ticket)

Derive `va_release` in this repo from `release` ⋈ `release_artist`, as a re-runnable derivation script wired into (a) both pipeline build paths so every monthly rebuild re-derives it after prune, and (b) `sync-library.sh` unconditionally, so the next daily run backfills prod automatically (no manual prod DDL session needed) and every daily run thereafter refreshes it. The daily refresh is load-bearing, not just convenience: LML inserts API-fetched releases (including VA comps) into the cache at runtime, and `rebuild-cache.yml`'s cron is disabled — an if-missing guard would freeze the table at its backfill snapshot indefinitely. Derivation is a sub-second `CREATE TABLE AS` over the ~50K-release prod cache, and no live request path reads `va_release` (only the build/canonicalization scripts do, sequentially in the same jobs), so a daily transactional swap is safe and cheap.

### Predicate (validated 2026-08-01 against the full 18.9M-release local dump)

`(ra.artist_id = 194 OR ra.artist_name = 'Various') AND ra.extra = 0`

- `artist_id = 194` is Discogs' canonical Various artist. In the full dump it covers 1,320,795 credit rows, of which 1,090 carry ANV names ≠ `'Various'` — a name-only predicate leaks those.
- `artist_name = 'Various' AND artist_id IS NULL` is 0 in dump data, but `release_artist.artist_id` is nullable for API-fetched rows (LML inserts these at runtime), so the name disjunct keeps API-inserted VA releases covered.
- `extra = 0` restricts to main-artist credits (238 dump rows have Various as an extra credit; those releases are not VA compilations).

### DDL (single transaction, atomic swap)

```sql
BEGIN;
DROP TABLE IF EXISTS va_release;
CREATE TABLE va_release AS
SELECT DISTINCT r.id, r.title, lower(r.title) AS norm_title
FROM release r
JOIN release_artist ra ON ra.release_id = r.id
WHERE (ra.artist_id = 194 OR ra.artist_name = 'Various') AND ra.extra = 0;
CREATE INDEX idx_va_release_norm_trgm ON va_release USING gin (norm_title gin_trgm_ops);
COMMIT;
ANALYZE va_release;
```

Deliberate divergences from the captured local DDL, documented in the script:

- **LOGGED, not UNLOGGED.** The local shell was unlogged; on Railway prod an unlogged table is truncated by crash recovery, which would silently regress the matcher to 0-row matching until the next rebuild. Consumers only see columns and indexes, so logged is a strict improvement. Derivation cost at prod scale (~50K-release cache, VA subset a few thousand rows) is trivial.
- **No FK to `release`.** Snapshot semantics: the table is re-derived after every rebuild; an FK would cascade-delete rows mid-rebuild (prune/dedup) and force the table into the LOGGED/UNLOGGED flip lists (`PIPELINE_TABLES`, see #105). No FK also means `TRUNCATE release CASCADE` in direct-pg mode and the import truncate lists never touch it — protected by omission, refreshed by derivation.
- **`norm_title = lower(title)` exactly.** Verified against all three consumer sites (`match_compilations.py` exact + trigram, `canonicalize_compilations.py` exact + trigram): the trigram paths compare `norm_title % lower($1)` (similarity absorbs diacritic drift), and both exact paths build Python-side `title.lower()` maps without reading `norm_title`. No unaccent.
- **No btree `idx_va_release_norm_exact`.** The captured local DDL had one, but no consumer queries `norm_title` by equality (the exact-match paths are Python-side, per the previous bullet) — it would be a dead index rebuilt on every derivation. Only the GIN trigram index survives.

`CREATE EXTENSION IF NOT EXISTS pg_trgm` runs first (idempotent; already present everywhere the pipeline runs).

### Why not alembic / create_database.sql

`va_release` is derived data, not durable schema: its contents are only correct relative to the current `release` ids, which drift every rebuild. An alembic revision would create it empty on existing DBs (useless without the derivation) and alembic's prod deploy wiring rides `rebuild-cache.yml`, whose cron is disabled — the daily-sync guard reaches prod ~24h after merge instead. Keeping the DDL solely in the derivation script gives it a single source of truth; `create_database.sql` stays untouched (a fresh DB gets the table at its first pipeline run's derive step). The `test_pipeline_tables_covers_all_release_fk_referrers` invariant is unaffected (no FK).

## Changes

1. **New `scripts/derive_va_release.py`** — importable `derive_va_release(conn, *, floor)` (psycopg, the repo's driver). CLI: **`--database-url` flag with the documented cache-database convention** — `--database-url` → `DATABASE_URL_DISCOGS` → `DATABASE_URL` cascade, hard error when all are absent, no localhost default — exactly the pattern of the automation-script family this script joins (`cache_health_metrics.py`, `check_cache_drift.py`, `check_override_parity.py`, etc.), which `sync-library.sh` invokes bare (env cascade) and `run_pipeline` invokes with an explicit `--database-url <url>`. **Row-count floor guard, enforced only when `va_release` already existed before the transaction**: after `CREATE TABLE AS` but before `COMMIT`, count the derived rows; below the floor (`--floor`, env `VA_RELEASE_FLOOR`, default **1**; 0 opts out) → `ROLLBACK` and exit non-zero, so a derivation that would produce an empty table never replaces a populated one (transactional DDL restores the pre-existing table on rollback). When no table pre-existed (the first-run backfill), the floor is skipped and even an empty derivation commits — an empty table is strictly better than the `UndefinedTableError` crash #344 fixes, and rollback-to-nothing would silently defeat the backfill forever. Default 1, not a speculative count: the prod library-scoped VA row count is unvalidated, and the guarded catastrophe is specifically empty-swap (e.g. the daily derive colliding with a mid-rebuild truncated `release` table); operators can raise `VA_RELEASE_FLOOR` once a prod baseline exists. Same abort-before-damage spirit as `STREAMING_APPLE_FLOOR` (`sync-library.sh:207-220`). Logs the derived row count; `lib.observability` logger init like sibling scripts. **Credential note**: the daily sync's `DATABASE_URL_DISCOGS` is the same repo-level secret `rebuild-cache.yml` uses for full public-schema DDL (the env comment in `sync-library.yml` says so explicitly), so the derive's `DROP`/`CREATE`/`CREATE INDEX` rights are the same ones the monthly rebuild already exercises.
2. **`scripts/run_pipeline.py`** — add `"derive_va_release"` to `STEP_NAMES` between `"prune"` and `"vacuum"`; new step block in `_run_database_build` (honoring resume state) and a call in `_run_database_build_post_import` after prune. Invoked via `run_step` subprocess like dedup/prune, **passing the resolved URL explicitly positionally**: `target_db_url if target_db_url else db_url` (exactly like vacuum), so copy-to mode derives on the DB consumers read — never relying on env fallback inside the pipeline. The pipeline invocation passes **`--floor 0`**: the floor's rollback semantics are only correct for the daily path (where the pre-existing table's ids are still current and worth keeping); after a rebuild the pre-existing table holds pre-rebuild ids — stale garbage — so publishing an honest empty derivation (loudly logged, surfaced by step logs and the drift-watchdog era of checks) beats rolling back to it. This also keeps the small-fixture E2E pipelines green regardless of what prune leaves behind. `_infer_pipeline_state` stays as-is — the step joins prune/vacuum in the "cannot be inferred, safe to re-run" class (docstring updated). Loading an old saved state file lacking the new step name must not crash and must run the step (verified: `wxyc_etl.PipelineState` returns `is_completed == False` for unknown steps and `mark_completed`/`save` tolerate them at version 3; add a test).
3. **`scripts/sync-library.sh`** — immediately before the recall-index block: `if ! "$PYTHON" scripts/derive_va_release.py ...; then log "WARNING: ..."; fi` — the file's established soft-fail idiom (the streaming-links block at :194-205 and the CTA block at :162-178 both use `if ! ...; then ... fi`, not `|| log`), with the sibling path style (`scripts/tsv_to_sqlite.py` at line 183; the script has already `cd`'d to `$REPO_DIR`; there is **no** `SCRIPT_DIR` variable in this file and `set -u` is not on, so a `$SCRIPT_DIR`-based path would expand empty and silently no-op). Must NOT touch `EXIT_CODE` (it gates both the recall-index build and the library.db release upload): a derivation failure must never block the upload path, and thanks to the floor-guard rollback it also can't clobber yesterday's good table — the recall-index build just runs against the previous derivation. This is the prod backfill delivery (first post-merge daily run creates the table) and the ongoing freshness mechanism (every later run re-derives).

## Post-review amendments (max-effort review of PR #345, 2026-08-01)

The shipped implementation diverges from the plan above in the following review-driven ways: the workflow keeps the full `[dev]` install AFTER the sync and adds a minimal soft-fail `psycopg[binary]` install before it (a hard pre-sync install would have made a transient pip failure take down the daily library.db upload, violating the invariant the LML-venv step documents; the minimal install also avoids newly activating wxyc_etl/sentry-sdk inside the sync-fatal tsv_to_sqlite step). `VA_RELEASE_FLOOR` is forwarded from a repo Actions variable (it was otherwise unreachable on the only production derivation path) and is resolved lazily and empty-tolerantly (the eager argparse-default parse crashed pre-parse on `VA_RELEASE_FLOOR=""` even when the caller passed `--floor 0`). The floor guard is keyed on pre-existing ROWS rather than table existence (an empty pre-existing table plus an empty derivation must commit cleanly, not raise a daily FloorViolation protecting zero rows). `derive_va_release()` rejects autocommit connections (the atomic swap and rollback silently degrade to destructive non-atomicity on one), takes a bounded `lock_timeout` (a collision with an in-flight rebuild must degrade into the soft-fail WARN, not stall the sync for the rebuild's wall-clock), probes `to_regclass` unqualified (so the probe and the DDL can never disagree via search_path), logs the credential-stripped target host/db before any DDL, and warns on the generic `DATABASE_URL` fallback. The pipeline step is gated on `library_db` exactly like prune (an unpruned multi-million-row build would pay minutes deriving a table nothing reads) and is soft-fail with a best-effort drop of the stale table (a transient failure must not discard a non-resumable multi-hour rebuild or strand tables UNLOGGED; absent-and-self-healing beats stale). `norm_title` is documented as PostgreSQL `lower()` semantics, which diverge from Python `str.lower()` for Turkish dotted İ and Greek final sigma — PG semantics are the consumer contract. An empty derivation from a populated `release` table logs a loud warning (the `--floor 0` rebuild path is otherwise unguarded and nothing monitors `va_release` yet).
