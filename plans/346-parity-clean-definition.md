**Three through-lines, each found repeatedly across review rounds. Anything added to this model has to be checked against all three.**

1. **Is the value resolved through a lookup table?** If so it carries that table's *stored* spelling, not a transform of the MySQL value. This covers `artists` (`artist`, `cross_reference_names`, `call_letters`) **and** `genres` / `format` (`genre`, `format`) — the ETL keys both maps on `.toLowerCase()` (`job.ts:951`, `:954`, `:966`, `:980`) while the export emits the stored `genres.genre_name` / `format.format_name` (`catalog-export.service.ts:233-234`). Deriving them is impossible; comparing case-insensitively (or under a fold) is correct. *This rule was originally written as "resolved through an `artists` row" and that scoping is exactly what let `genre` and `format` sit misclassified as derivable for two revisions — the mechanism is the lookup, not the table.*
2. **What does the ETL do to the value on the way in?** "Derivable" does not mean "identical". Four of the diffed columns are tab/newline-substituted in the extraction SQL; both call-number columns coerce NULL to `0`; and the two producers pass different `mysql` client flags, so every text column diverges on embedded backslashes. Each unmodelled transform is a whole row-population classified as defects forever — which is the exact failure this plan exists to prevent, so assuming identity is the thing to be most suspicious of.
3. **Does the surface actually gate?** If it feeds `clean`, it needs the same modelling as the columns — no exceptions for being a side table. `compilation_track_artist` sat inside the verdict for three revisions with a bare `_normalize` comparison and no drop-path enumeration, which would have frozen an escaping artifact into the release gate. Enumerate what gates, then model each entry.

## Problem

`scripts/catalog_parity_diff.py` compares MySQL-sourced and Backend-sourced `library.db` files field-by-field with a single generic `_normalize` (NULL / empty / literal `"NULL"` / surrounding whitespace). Against a *healthy* production pair on 2026-08-12 that reports:

- ~30,700 field mismatches, of which ~30,000 are deliberate Backend normalizations
- 609 missing in Backend, 191 extra in Backend — of which 724 rows are documented, non-backfillable residue and 76 are legitimately-minted new releases

So wiki#89's AC#4 — "7 consecutive clean parity days" — is **not satisfiable by any state of the data**. The soak cannot start, which makes this the only remaining dependency on step 4. Steps 3 and 5 are gated elsewhere (BS#2109/dj-site#1161, BS#2108); this one is gated on nothing.

The [wiki#89 baseline comment](https://github.com/WXYC/wiki/issues/89#issuecomment-5273611094) proposed encoding "the five normalization classes" as expected. That framing is available but weaker than what the code allows.

## Part 1 — Model every diffed column, deriving the expectation where the ETL is deterministic

Most of the ~30,000 deliberate normalizations are the output of three functions in `Backend-Service/jobs/library-etl/job.ts`:

| Function | job.ts | Produces baseline classes |
|---|---|---|
| `normalizeArtistName` | `:79-89` | `artist` VA genre-suffix dropped (2,495) |
| `normalizeCodeLetters` | `:102-113` | `call_letters` uppercased (15,769); unanchored `/Z-[A-Z]/` → `V/A` |
| `parseFormatAndDiscs` | `:115-146` | `format` separator dropped (4,854) + multi-disc `x N` (660) + `vinyl - LP`→`vinyl 12"` (297) |
| the `isVarious` branch — not a function | `:993-996` | `call_letters` → `V/A` (6,338)¹ + `artist_call_number` → `0` |

¹ **`Z--` does not match the regex, and it is the largest `Z-` population.** `/Z-[A-Z]/` (`job.ts:106`) requires a letter after the hyphen, and `-` is not one — so `normalizeCodeLetters("Z--")` falls through to the 3-char branch and returns `"Z--"` unchanged. On the 2026-07-19 prod snapshot `Z--` is **3,104 rows**, more than every genuine `Z-[A-Z]` code combined (`Z-S` 401, `Z-B` 244, `Z-M` 224, `Z-T` 216, …). So the 6,338-row `V/A` class does not come from that function at all: `job.ts:993-996` reads `codeLetters = artistInfo.isVarious ? 'V/A' : normalizeCodeLetters(...)`, meaning on a VA row `normalizeCodeLetters` is **never called**, and on a *non*-VA `Z--` row Backend holds `Z--`. Two populations a column-independent model silently merges — and an implementer writing step 2's cases from the old single-row table would have asserted `V/A` for 3,104 rows that keep `Z--`. Hence the split table and an explicit `Z--` red case. The row-awareness is the point: `call_letters` and `artist_call_number` are both functions of the *artist* field, not of themselves.

Port those to Python and **derive what Backend should hold** from the MySQL row. Each field classifies as **agree** (`backend == mysql`), **normalized** (`backend == expected(mysql) != mysql` — counted, not drift), or **mismatch** (Backend disagrees with its own ETL's spec — a genuine defect).

Two reasons this beats enumerating classes:

1. **It sizes defects correctly by construction.** BS#2116's "395 rows lost their format qualifier" was 5 real defects plus ~390 false positives from the `cd x N` family. Pattern-matching reproduces that 79× error; replaying `parseFormatAndDiscs` separates them, because `cd x 2 → cd` *is* the spec while `vinyl - 12" → vinyl` violates it.
2. **The contract fixtures already exist.** `Backend-Service/tests/unit/jobs/library-etl.test.ts:169-206` and `:225-296` unit-test all three (the intervening `toAlphabeticalName` block at `:207-224` feeds `alphabetical_name`, which is not a diffed column, and is not ported); `tests/unit/database/fold-artist-name.test.ts` pins the fold. Those port directly, including carve-outs a reimplementation-from-description would miss — `/^various\s*artists\s*-rock\s*-[a-z]$/i` staying literal (`:200-205`), `normalizeCodeLetters`'s **unanchored** `/Z-[A-Z]/`, 3-char-uppercase vs first-2-uppercase.

**No schema change needed.** `disc_quantity` is not in the daily-sync shape (`lib/library_db.py:46-63`) and adding it would touch production sync, `tsv_to_sqlite.py`, and the Backend export contract. Deriving the format *name* sidesteps it. Recorded assumption: the `x N` count is unverified here — BS#2116 measured `disc_quantity` agreeing with tubafrenzy's `x N` on **0 of 64,067** common releases.

### `artist` needs a fourth tier, because the ETL is not deterministic there

The 603 "canonicalized" rows are **not** produced by `normalizeArtistName`, which only trims and VA-folds. They come from `ensureArtist` (`job.ts:375-434`), which resolves an existing row via `fold_artist_name(artists.artist_name) = fold_artist_name($name)` and returns **`existing[0].artist_name` — the stored spelling** (`:429-433`). What Backend writes depends on database state, not on the MySQL value; no replay reproduces it.

So `artist` classifies on four tiers: agree → derived-normalized → **fold-equal** (counted as normalized) → mismatch. The fold is migration `0134_fold-artist-name.sql`:

```sql
lower(regexp_replace(normalize(coalesce(input, ''), NFD), '[̀-ͯ]', '', 'g'))
```

NFD → strip Combining Diacritical Marks U+0300–U+036F → lowercase. It deliberately does **not** strip a leading "The " (that is `normalize_artist_name`, migration 0092) — porting that by mistake would newly merge "The Notwist" with "Notwist". TypeScript twin: `shared/database/src/fold-artist-name.ts`.

### Model for all ten diffed columns

`DIFF_COLUMNS` is `LIBRARY_COLUMNS` minus `id` and `label`. Stating each so none is silently unmodelled:

| Column | Model | Group |
|---|---|---|
| `artist` | TAB/NL sub → `normalizeArtistName` → fold tier | artist-resolved |
| `call_letters` | `normalizeCodeLetters(...) or '??'`, VA override from `artist`, **case-insensitive** | artist-resolved |
| `cross_reference_names` | **multiset compare under the fold tier**, split on the imported `CROSS_REFERENCE_SEPARATOR` (`catalog_parity_diff.py:120`) | artist-resolved |
| `artist_call_number` | `0` when VA, **else `?? 0`** | derivable + crossref-resolved (see below) |
| `release_call_number` | **`?? 0`** | derivable |
| `format` | `parseFormatAndDiscs`, then **case-insensitive** | lookup-resolved |
| `genre` | **case-insensitive** | lookup-resolved |
| `title`, `alternate_artist_name`, `album_artist` | TAB/NL sub, then byte-identical | derivable |

**The model is keyed by column name and asserted against `DIFF_COLUMNS`, because a static table re-creates the blind spot the derivation was built to close.** `DIFF_COLUMNS` is deliberately *derived* — `catalog_parity_diff.py:139-149` says a new column "must widen the diff automatically, or it becomes a permanently-undiffed blind spot". A ten-row table written by hand defeats that: add a column to `LIBRARY_COLUMNS` and it falls through the classifier's default branch, silently unmodelled, inside the tool that certifies the cutover. So `COLUMN_MODELS` is a dict and a step-3 test asserts `set(COLUMN_MODELS) == set(DIFF_COLUMNS)`, mirroring `test_select_statements_match_sync_library_sh` (`tests/unit/test_catalog_parity_diff.py:2081-2099`) — set equality, not containment, so a *removed* column fails too.

**Both call-number columns coerce NULL to 0, on every branch.** `job.ts:996` is `isVarious ? VARIOUS_ARTISTS_CODE_NUMBER : (release.artist_call_numbers ?? 0)` — the `?? 0` covers the **non-VA** branch too — and `job.ts:1100` is `code_number: release.release_call_numbers ?? 0`. Meanwhile `_normalize` (`catalog_parity_diff.py:176-193`) collapses NULL and `''` to `None`, and `None != 0`. Without modelling the coercion, **every legacy row with a NULL `CALL_NUMBERS` is a permanent mismatch** on one or both columns.

This also narrows the measure-first scope: the `?? 0` half of `artist_call_number` is fully deterministic. Only the `ensureGenreArtistCrossref` last-write-wins coupling on `(artist_id, genre_id)` (`job.ts:456-470`) needs the measure-first posture, not the column as a whole.

**Four of the diffed text columns are tab/newline-substituted at extraction, and the harness's SELECT does not do it.** `buildReleaseQuery` wraps `TITLE`, `ALTERNATE_ARTIST_NAME`, `PRESENTATION_NAME` (→ `artist`), and `ALBUM_ARTIST` in `REPLACE(REPLACE(IFNULL(<col>, ''), '\t', ' '), '\n', ' ')` (`job.ts:281-296`) — plus a fifth, `lc.ALPHABETICAL_NAME` (`:295`), which feeds no diffed column and so enters no model; it is named here so the five-wide `REPLACE` set in the SQL is not re-derived as a discrepancy against this paragraph. `LIBRARY_SELECT_SQL` (`catalog_parity_diff.py:509-524`) has no such wrapper. Deterministic and row-derivable, so it belongs in the `normalized` tier — and it must be applied *before* `normalizeArtistName`, since the SQL-level replace runs first. This is the **only** remaining stage of the model, for the reason below.

### The escaping asymmetry is a production defect, and it gets fixed in the producer

The two producers do not escape the same way. Backend's `MirrorSQL` runs `mysql ... --batch --raw --silent` (`shared/database/src/legacy/sql.mirror.ts:82`, and again at `:93` for the docker path), and `--raw` **disables** escape conversion. The harness (`catalog_parity_diff.py:1425`) and `scripts/sync-library.sh:149` run `-B -N` **without** `--raw`, which escapes — `sync-library.sh:167` says so outright: "`-B -N` already escapes embedded tab/newline/**backslash** bytes".

R8 proposed absorbing that as stage 1 of the harness's derivation. That is the wrong home for it: **`parse_library_tsv` never unescapes, and it feeds production.** It maps only `\N`→`None` (`lib/library_db.py:219-240`), and its consumers are `scripts/tsv_to_sqlite.py:61` — the nightly `sync-library.sh` path that builds the `library.db` **LML serves searches from** — and `catalog_parity_diff.py:1468`. So a title or artist containing a tab would reach the served catalog as a literal backslash-`t`, and one containing a backslash as `\\`. That belongs to the shared producer, not to Backend's normalization spec, and burying it in a harness-only module would classify it as "expected" forever — in the module whose own docstring (`lib/library_db.py:9-16`) exists "so the two producers cannot drift apart in shape".

**Measured before being believed: the affected population is currently empty.** R8 and R9 both wrote this up as an *active* production defect. It is not. Against the most recent prod snapshot (`lml-cutover-snapshots/prod-20260719/library.db`, 64,815 rows), **zero rows carry a backslash, tab, newline, or NUL byte in any of the seven text columns that snapshot has** — `title`, `artist`, `call_letters`, `genre`, `format`, `alternate_artist_name`, `album_artist`. Controls confirm the query rather than the emptiness: `instr()` locates a backslash in a literal, 3,948 titles contain an apostrophe, and 10 carry multi-byte UTF-8, so unescaped free text is plainly present and surviving.

Three consequences, all of which lower the stakes of step 1 rather than raise them:

- **This is a prophylactic producer fix, not a repair.** It changes no served byte today. The correct claim in the PR body is "latent, measured at 0 rows on the 2026-07-19 snapshot", not "fixes corrupted output".
- **It contributes nothing to the ~30,700 mismatches** and does not move the gate. It is in scope because it is cheap, because it keeps the model at one stage instead of two, and because the failure it prevents is silent — a librarian pasting a tab-bearing title would corrupt search with no error anywhere.
- **`compilation_track_artist` is unmeasured.** No local snapshot has the table (every copy on this machine predates it, newest 2026-04-23), so the CTA columns get the same count in step 1 against a live source before the framing above is asserted of them too.

**`\0` is the one escape whose disposition is not obvious, and it stays undecided on purpose.** `mysql --batch` escapes NUL as `\0` alongside the other three, so a faithful unescape writes a real NUL into `library.db` TEXT — which Python's `sqlite3` carries fine but which truncates the value for any `sqlite3_column_text` consumer downstream, in the artifact LML uploads and serves. Fidelity to the wire and not-corrupting-the-served-catalog point opposite ways here, and Backend's `--raw` path has the identical exposure, so this is not a harness-side choice at all. Measured NUL count on the snapshot is **0** across the same seven columns. Deciding the tie-break now, against zero observed rows, would be the R8/R9 mistake a third time — so step 1 unescapes `\0` to NUL for consistency with the other three, and if the live re-measurement finds any row at all, that opens a ticket rather than a snap judgement in this plan.

The `--raw` asymmetry itself remains real and worth encoding regardless of today's count: it is a standing difference between the two producers, and the population is empty only because the source data happens to be clean.

So the unescape lands in `parse_library_tsv` and `parse_compilation_track_tsv`, applied per field **after** the split on real tabs (the escaping happens on the wire, so splitting stays safe — that is what `lib/library_db.py:251-255` documents). It must be a **single left-to-right pass** — `\\`→`\`, `\t`→TAB, `\n`→NL, `\0`→NUL — not a sequence of `str.replace` calls. Its own test case proves why: for source data containing backslash-then-`t`, the wire carries `\\t` (three chars) while Backend holds `\t` (two — `--raw`, and the SQL `REPLACE` finds no real tab to substitute). A left-to-right `.replace("\\t", " ")` matches at offset 1 and yields backslash+space, a false mismatch that also corrupts the value the fold tier then sees. The single-pass unescape consumes `\\` first and gets it right. **The embedded-backslash case is a red test, not a note.**

**And it must run *after* the `\N` NULL test, not before.** Both parsers map the wire field `\N` (two chars) to `None` — `lib/library_db.py:240` and `:267-269`. A field whose source data is a literal backslash-`N` arrives on the wire as `\\N` (three chars); unescape first and it becomes `\N`, which the sentinel test then reads as SQL NULL. That is silent data loss *introduced by the fix*, in the production path the fix exists to protect. So the order is pinned: split → test `== "\\N"` on the **raw** field → unescape only the survivors. Same hazard class as the `.replace("\\t", " ")` case above — a two-char sentinel colliding with an escaped three-char sequence — and it gets its own red case beside it.

Two consequences worth being explicit about:

- **This PR can change the bytes production serves** — strictly as a correction (literal `\t` → real TAB) — but on the measurement above it changes none. It stays a separate commit from the harness work, and step 1 re-measures against the live catalog (including the CTA columns, which no local snapshot has) so the PR body states a current number rather than a stale one.
- **The model collapses to one stage.** With both sides carrying true bytes, the only remaining derivation is Backend's own TAB/NL→space on the four wrapped columns. `genre` needs no unescape step at all, which is why its row in the table above is now just the case-insensitive compare.

Recorded fragility: the fix depends on Backend using `--raw` and this repo not. A flag change on either side silently invalidates it, so all three call sites are named in the `parse_library_tsv` docstring.

**`genre` and `format` are lookup-resolved too, which the model table now reflects.** `genreMap` / `formatMap` are keyed on `.toLowerCase()` (`job.ts:951`, `:954`) and looked up that way (`:966`, `:980`), while the export emits the stored `genres.genre_name` / `format.format_name` (`catalog-export.service.ts:233-234`). Any case drift between tubafrenzy's `GENRE.REFERENCE_NAME` and Backend's `genres` table is absorbed silently at import and would reappear here as a whole-column mismatch population. Comparing case-insensitively costs nothing and removes the blind spot; a *rename* on either side remains invisible to this harness and is recorded as such.

**`call_letters` has a `'??'` fallback *and* a casing coupling.** `ensureArtist` computes `normalizedLetters = codeLetters ?? '??'` (`job.ts:387`) and inserts it (`:441`), so a MySQL row with empty `CALL_LETTERS` — 69 such codes per `residue-ledger.md:65` — holds `'??'` where a bare `normalizeCodeLetters` yields `null`. Separately, the export emits `artists.code_letters` (`catalog-export.service.ts:229`) while `ensureArtist` *resolves* on `lower(artists.code_letters) = lettersLower` (`job.ts:411`, `:421-423`) and returns only `{id, artist_name}` — so an artist row created by dj-site or an older ETL keeps its own casing, which `normalizeCodeLetters`'s unconditional uppercase would flag as a defect. Compare case-insensitively.

**`cross_reference_names` is the same coupling as `artist`, not a plain set compare.** The crossref import resolves each alias through `findArtistId` (`job.ts:491-519`), which matches on `fold_artist_name(...)`; the export then emits the **stored** spellings via `array_agg(DISTINCT artists.artist_name ...)` (`catalog-export.service.ts:201-203`), while MySQL emits raw `LIBRARY_CODE.PRESENTATION_NAME`. A bare set compare would classify every accent/case difference as a defect, plus the entire 271-row "collapsed onto a shared key" class from `residue-ledger.md`.

So it compares as a **multiset of `fold(normalizeArtistName(x))`**, under the same tiers as `artist`. Order is irrelevant either way: MySQL uses `GROUP_CONCAT(DISTINCT ...)` with **no `ORDER BY`** (`catalog_parity_diff.py:512-521`), Backend an ordered array (`:694-700`).

**Cardinality loss does not gate — it is reported and sized first.** Backend can hold fewer aliases than MySQL for two byte-indistinguishable reasons:

1. **Fold-collapse** — two MySQL aliases folding to one Backend artist, which `array_agg(DISTINCT ...)` emits once.
2. **Never-imported crossrefs** — `importReleaseCrossrefs` skips a row whenever its artist/genre/album lookup misses, cascading from the dropped releases. `residue-ledger.md` measures this as **41 of 119** artist-code crossrefs and 13 of 35 release crossrefs, and D5 **freezes** artist-code crossrefs at cutover — so this set never goes to zero.

Nothing in the row distinguishes the two, and treating either as a mismatch pins `clean` false permanently. So `cross_reference_names` cardinality deltas ship as a **reported residual**, the same measure-first posture as `artist_call_number`, sized against the ledger's 41/13 in step 8 before any decision to let them gate.

**`artist_call_number` is measured before it is judged.** The export emits `genre_artist_crossreference.artist_genre_code` (`apps/backend/services/catalog-export.service.ts:231`), written by `ensureGenreArtistCrossref` as a **last-write-wins upsert on `(artist_id, genre_id)`** (`job.ts:462-470`). For non-VA rows `artistGenreCode` is part of the artist lookup key (`:389`, `:423`), which *should* make it self-consistent; but the VA branch resolves without it, and Backend's own artist-add path (`apps/backend/services/library.service.ts:1858-1887`) can pair an artist with a code this ETL did not choose. That is the same class of DB-state coupling `artist` was conceded. Posture: ship the simple model, **report the residual, and do not call a delta a defect until the prod run sizes it.** If non-zero, it gets a tolerance tier and a follow-up ticket — not a silent "expected".

### `compilation_track_artist` gates `clean` and had none of this applied

The CTA multiset is inside the verdict (Part 3), so through-line #3 makes it a modelled surface, not a side table. Today `_load_cta_counts` (`catalog_parity_diff.py:261`) compares the three `CTA_COLUMNS` with a bare `_normalize`, against a `COMPILATION_TRACK_SELECT_SQL` (`:529`) that has no `REPLACE` wrapper. Backend's side (`job.ts:722-731`) wraps three columns in the same `REPLACE(REPLACE(...), '\t', ' '), '\n', ' ')` — `ARTIST_NAME`, `TRACK_TITLE`, and `TRACK_POSITION`, the last of which is not in the CTA diff shape and needs no modelling — and runs under `--raw`. Identical asymmetry, unmodelled.

There is also an unenumerated CTA drop path: `parseLegacyCompilationTrackRows` discards any row whose trimmed `ARTIST_NAME` is empty (`job.ts:710-711`), *plus* the `parseTabRow(line, 4)` column-count drop above it (`:705-708`) — the CTA analogue of library skip-path 8. Neither is in the ledger, so both currently land as `cta_missing`.

So the CTA multiset gets: the producer unescape (already covered — `parse_compilation_track_tsv` is fixed in the same commit), Backend's TAB/NL substitution on `artist_name` and `track_title`, and the empty-artist drop as a rule-derived expected-missing predicate. **Note the SQL itself does not change on either side** — `test_select_statements_match_sync_library_sh` pins `COMPILATION_TRACK_SELECT_SQL` to `sync-library.sh`, and altering it would change the production TSV. The modelling is Python-side, exactly as it is for the library columns.

This lands in step 3, *before* step 6 re-derives the CTA baseline. The ordering is the point: baselining first would freeze an escaping artifact and a drop path into the release gate, which is this plan's own stated failure mode.

New module `lib/backend_catalog_norm.py`. Its docstring names the source file, functions, and porting commit — and states why it is **not** `lib/format_normalization.py`, whose `normalize_library_format` maps into a different category space (`"Vinyl"`, not `vinyl 12"`) for a different purpose, so nobody consolidates them later. It also records that the export reads `COALESCE(library.artist_name, artists.artist_name)` (`catalog-export.service.ts:220`) — a denormalized copy frozen at insert (`job.ts:1094`; `shared/database/src/schema.ts:604`, nullable until the A.2 backfill). The two agree for ETL-written rows, so the fold tier holds today, but a later rename in `artists` leaves the stale copy winning; naming both sources keeps the tier's scope explicit.

## Part 2 — Rules where the set moves, enumeration where it is frozen

**Rule A — minted ids.** `extra_in_backend` where `id >= 1_000_000` is expected by construction: BS#1963 mints there, those releases have no tubafrenzy counterpart, and the set *grows during the soak* as librarians add through dj-site (wiki#89 step 2 runs concurrently). Enumerating it would go stale within a day and fail the gate precisely when the migration is working.

**Rule B — deliberate ETL row skips.** `LIBRARY_SELECT_SQL` has no `WHERE`, so skipped rows are present MySQL-side and show as missing. There are **seven** skip paths, not five, and they do not all live in one range:

| # | Skip | job.ts | Row-derivable? |
|---|---|---|---|
| 1 | `db_only` genre | `:960` | **Yes** — `isDbOnlyGenre`: `genre is not None and genre.strip().lower() == 'db_only'` (`job.ts:75-77`), **not** a bare `== 'db_only'` |

This rule-vs-enumeration split matters because `residue-ledger.md:38` says of the frozen 12: *"`db_only` is still being used, so this set grows slowly while `/wxycdb` stays open."* A frozen list goes stale for exactly the reason Rule A exists.

- The **flowsheet-referenced orphans D10 keeps**. Two distinct ledger states, and the soak opens in the second. **A ledger id absent from today's diff is reported in the JSON, not a failure** — a stale entry should be visible without resetting a 7-day streak.

**Ledger file — follows the vendor/pin split, because that is what the precedent actually is.** `wxyc-etl-pin.txt` is *not* a root-level data file: the canonical bytes live in `vendor/wxyc-etl/` (three files) and the root pin carries only SHAs plus a refresh procedure. Vendoring cross-repo residue data is exactly that shape, so:

- `vendor/parity-residue/` — the id sets, converted to JSON.
- `parity-residue-pin.txt` — SHAs, measurement date, the re-derivation query/procedure, a note per set.
- `scripts/vendor_parity_residue.py` — the conversion, run by hand.

**The pin has no upstream to point at, and it must say so.** `wxyc-etl-pin.txt` works because it pins a released **tag** (`wxyc_etl_version = 0.4.0`) with a "re-vendor from a new tag, bump the SHAs, run the parity test" procedure. Here there is no tag and no commit — the source artifacts are untracked (below) — so a "source commit" field is unfillable and the pin degrades to a self-hash. That is still the load-bearing half: it catches a hand-edit of `vendor/parity-residue/*.json`, which is the realistic failure. What it *cannot* catch is a wrong vendoring, and pretending otherwise is worse than admitting it. So `parity-residue-pin.txt` states in its own header that **`vendor/parity-residue/` is the source of truth**, and carries the re-derivation procedure plus a measurement date in place of a provenance pointer. If the four artifacts later land in a WXYC org repo, the pin gains a real commit field and this paragraph is what explains why it did not have one.

**The source is a personal repo, and the artifacts are not committed in it.** **Four** files live at `plans/tubafrenzy-phase3-close-out/` in `jakebromberg/wxyc-workspace` — not a WXYC org repo — and all four are currently **untracked even there**: `residue-collapsed-599.tsv`, `residue-orphan-115.txt`, `residue-absent-12.txt`, and `residue-ledger.md`.

**Only two of the four get vendored, and why the other two don't is part of the design.** `residue-collapsed-599.tsv` is the frozen enumeration Rule B cannot derive, and `residue-ledger.md` is the provenance narrative the pin cites in place of a commit. `residue-absent-12.txt` is **not** vendored: that set is Rule B's *output*, re-derived per row from skip paths 1/3/5/6, and freezing it reintroduces exactly the staleness `residue-ledger.md:38` warns about ("`db_only` is still being used, so this set grows slowly"). `residue-orphan-115.txt` is not vendored either, for a different reason — it is superseded by BS#2108's emitted kept-set, and pinning today's 115 would freeze the pre-delete state into a post-delete gate. A partial vendoring with no stated reason reads as an oversight, so the pin header names both exclusions. So the input to a release gate exists only on one laptop. Vendoring is therefore not a convenience; it is the step that makes the gate reproducible at all, and it must land before the soak. Two consequences: the conversion script **cannot run in CI** (its source repo is never checked out), so its test operates on a small committed sample rather than the live path; and the org-repo copy under `vendor/` becomes the citable artifact for anyone re-running the soak.

## Part 3 — The `clean` verdict, including compilation tracks

`ParityDiff` is a `@dataclass(frozen=True)` whose docstring pins declaration order to the `--json` contract with the two id lists **last** (`catalog_parity_diff.py:158-173`). New fields therefore go **before** `missing_in_backend_ids` / `extra_in_backend_ids`, and `normalizations` carries a `default_factory` regardless:

**Field order is constrained by the dataclass, not by taste.** `matched` through `cta_extra` (`:166-171`) carry no defaults, and Python forbids a non-default field after a defaulted one — so `normalizations` (which needs a `default_factory`) must come *after* the plain ints, or the class raises `TypeError` at import. The full declaration order, stated once so `--json` has an unambiguous contract:

```
matched, missing_in_backend, extra_in_backend, field_mismatches, cta_missing, cta_extra,   # existing, unchanged
clean, missing_unexplained, missing_expected, extra_unexplained, extra_expected,           # new, no defaults
normalizations,                                                                            # new, default_factory
missing_in_backend_ids, extra_in_backend_ids                                               # existing, default_factory
```

New fields **append after `cta_extra`** rather than leading with `clean`, so the existing `--json` key *set* keeps its order. Semantics: `clean` is true only on zero unexplained missing, zero unexplained extra, zero field mismatches, **and** CTA within its documented baseline. `normalizations` is **reported, not gating** — a change in its shape is a signal, but should not fail a day. Its key space is pinned: **column → class** (`dict[str, dict[str, int]]`, e.g. `{"call_letters": {"uppercased": 15769}}`), the same pairs as Part 1's table rows, and the ledger's `baselines` block (Part 2 / step 4) carries the identical shape — so the step-6 baseline comparison is key-for-key, never a re-aggregation across two different groupings. Part 4's architecture.md edit lists the keys in exactly this order.

**`field_mismatches` changes meaning, and that is a bigger deal than the new keys.** `clean` requires "zero field mismatches", which is only reachable because `field_mismatches` stops counting the ~30,000 deliberate normalizations it counts today (`catalog_parity_diff.py:294-299`). Its value drops from ~30,700 to ~700 and the removed volume reappears under `normalizations`. Stable key names with silently changed semantics are worse for a consumer than a new key would be, so the redefinition is stated explicitly here, called out in the `architecture.md:139` edit alongside the exit-code sentence, and noted in the module docstring. One shape constraint rides with it: `field_mismatches` stays **fully keyed over `DIFF_COLUMNS`, zeros included** — `_print_human` subscripts it directly for every column (`:1539-1540`, no `.get()`), so a tiering change that stops emitting a zero-count key turns the default invocation into a `KeyError`. A step-3 test asserts `set(field_mismatches) == set(DIFF_COLUMNS)` on a diff with no mismatches at all.

**The seam that carries the ledger in — and what does *not* depend on it.** `run_diff(mysql_db, backend_db)` (`:318`) and `diff_library_dbs(mysql_conn, backend_conn)` (`:275`) take no ledger today, and the per-column loop (`:294-299`) has no row-level hook; there are 22 call sites in `tests/unit/test_catalog_parity_diff.py`. Both gain an optional trailing `ledger: ResidueLedger | None = None`.

The split matters, because R7 left it ambiguous in a way that would have made one `--json` key mean two things:

- **Field tiering is unconditional.** It is a correctness fix to the comparison itself and has no logical dependence on the residue *id sets*. So `field_mismatches` drops to tier-3-only **always**, with or without a ledger, and `architecture.md:139` states that flatly. The 22 existing call sites therefore change expectations — a planned edit, not preserved behaviour. (R7 claimed the seam "preserves today's behaviour exactly when absent"; that was the ambiguity.)
- **Row-level expected/unexplained classification and `clean` require a ledger.** Without one, `missing_expected` / `extra_expected` are 0, everything lands unexplained, and `clean` is `null` rather than false — absent, not failed.
- **`--residue-ledger` defaults to the vendored path**, so the soak needs no argument and the ledger is present in practice. **That default resolves from the module, never from the cwd** — `Path(__file__).resolve().parent.parent / "vendor" / "parity-residue" / <file>.json`. A cwd-relative default combined with "a missing ledger exits 3" (below) would fail every invocation launched from anywhere but the repo root, starting with the `mktemp -d` block at `docs/architecture.md:177-182` that an operator copies to run the soak — the gate would break on the one workflow it exists to serve. The repo already settles this: `alembic/versions/0004_wxyc_identity_match_fns.py:85-86` anchors on a module-level `_REPO_ROOT` and `tests/integration/test_wxyc_identity_match_parity.py:35` uses `Path(__file__).resolve().parents[2]`. A step-5 test resolves the default from an arbitrary cwd. **`--residue-ledger none` is the spelling for "no ledger"** — needed because R8 left the ledger-less mode with no way to *reach* it: with a default that always resolves, "no ledger" could only have meant a missing vendored file, which is a different condition. Without the explicit spelling the exit-2 rule below was unreachable and its test unwritable.
- **`--fail-on-drift` combined with `--residue-ledger none` exits 2**, detected at argument-parse time. It is a contradiction in the invocation — asking to fail on drift while refusing the definition of expected drift — which is what exit 2 already means here (`:1563`, `:1568`).
- **A missing, unreadable, or malformed ledger exits 3**, matching the existing `SourceError` contract (`:1596-1598`) — it is a source the run depends on, exactly like an unreadable `library.db`.

**Baselines live in the ledger, not in a flag.** R3 asserted normalization stability "via `--baseline`" and made `clean` depend on a "documented CTA baseline" without ever specifying where either comes from — as written `clean` was not computable. Both are `baselines` blocks inside the vendored ledger: the per-class normalization counts and the CTA missing/extra pair, each with its measurement date. That keeps it to one `--residue-ledger` flag, versions the baseline alongside the id sets it belongs with, and makes a baseline change a reviewed diff rather than an operator's command-line argument.

**CTA is in the gate.** `cta_missing` / `cta_extra` are populated from real data on both sides, so omitting them would certify the cutover while compilation-track membership silently diverges. But it cannot gate on D6's number as written: D6 documents 4,161 extra, while the 2026-08-12 run measured **2,771 missing / 6,932 extra**. That discrepancy is unexplained, and BS#1996's 5,310-row mojibake cohort is a plausible but unverified part of it — as is the escaping asymmetry and the empty-artist drop, both unmodelled until R9. **Part 3 ships the plumbing and reports CTA; the CTA baseline must be re-derived and classified before the soak starts** — its own step, not silently absorbed — and it is re-derived only *after* Part 1's CTA modelling lands, so the number it freezes is a modelled residual rather than an artifact. Until then `clean` treats a CTA delta outside the recorded baseline as unexplained.

**Three output surfaces, not one.** The `--json` contract is only what CI reads. An operator running the default invocation goes through `_print_human` (`catalog_parity_diff.py:1530-1544`), and `main`'s closing `logger.info("catalog parity diff complete", extra={...})` (`:1609`) carries a fixed key set. All three get `clean` plus the unexplained counts, or the default invocation never shows the verdict. Log tags follow `docs/observability.md`.

**The drift exit code is 4, not 1.** R3 picked 1 as "the only unused value". It is unused *on purpose*: the blanket `except Exception` at `:1586-1592` exists so a producer failure does not "escape as a raw traceback and exit 1". Reusing 1 would make an interpreter-level crash and a drift verdict indistinguishable to a CI runner — precisely inverting that comment's intent. So `--residue-ledger PATH` and `--fail-on-drift` (**exit 4**), with 0 = ran, 2 = bad args, 3 = source error, 1 = crash, all preserved. Default behaviour unchanged.

## Risk: historical spec drift

Replaying today's `job.ts` against rows written by older versions will surface any row whose stored value predates a spec change as a `mismatch`. Real divergences, not necessarily cutover-blocking, volume unknown. The fold tier absorbs the largest known instance (`artist`); the `'??'` fallback absorbs the second. The rest is unquantified.

Mitigation: ship the model and tests, then run against the real prod pair before calling the definition final. If the residual is not small and explainable, **that measurement is the deliverable** and classification gets a follow-up ticket — it does not get absorbed into "expected".

## Step 9 — fold-collapse widening (added after step 8's measurement)

Step 8 said "if the residual is not small and explainable, that measurement is the deliverable and classification gets a follow-up ticket". The residual was **131**, and it turned out to be both small *and* explainable — 103 of it by a single property of the source — so the follow-up is this widening rather than a ticket.

**The finding.** tubafrenzy identifies an artist by `LIBRARY_CODE` row; 295 presentation names have more than one (596 code rows, 542 carrying releases). Backend identifies by `artists` row via `fold_artist_name`, so duplicates collapse into one row holding a single `code_letters` and a single `artist_genre_code` per `(artist, genre)`. Releases filed under the losing code diverge against a value that is legitimate but belongs to a sibling. That one fact produced `artist_call_number` 59 + `call_letters` 33 + `cross_reference_names` 11 = 103.

**Why widen rather than change the `clean` term.** This is the same argument the ledger already makes for the 599 collapsed releases — MySQL has two rows where Backend correctly has one — applied to fields instead of rows. Relaxing `sum(field_mismatches) == 0` instead would weaken the check for every *other* column to solve a problem in three of them. And the alternative fix, deduplicating 295 names in tubafrenzy, is librarian work that will not happen before 2026-08-31.

**Design.** Fold-collapse is not a property of a row *pair*, so it does not belong in `COLUMN_MODELS`: deciding it needs the whole mysql side, because the explanation lives in a sibling row. `call_letters` and `artist_call_number` resolve in `_classify_matched_rows` (which already holds both full maps) against a fold-keyed index, reporting `fold_collapsed`. `COLUMN_MODELS` stays per-pair and pure, and the 22 existing call sites are untouched.

`cross_reference_names` is the exception, and instructively so: it collapses the same way but as a *set union*, so the widening is expressible per row. `LIBRARY_CODE_CROSS_REFERENCE` is joined per code while `LIBRARY_SELECT_SQL` only reaches codes carrying a release — so a duplicate code with zero releases is structurally invisible to this harness while Backend still folds it in. All 11 prod rows were strict supersets. That makes a superset `cardinality_gain`, the exact symmetric counterpart of the `cardinality_loss` branch already there, resting on the identical "the row cannot distinguish the causes" argument. The earlier docstring's claim that a superset is "a genuine defect" was wrong structurally, not by degree.

**What stays gated** — the whole design turns on these, and each has a negative test:

- The value Backend holds must be one the folded artist's own mysql rows *supply*. Having duplicates is never itself sufficient.
- `artist_call_number` is scoped to the row's own genre (`ensureGenreArtistCrossref` keys on `(artist_id, genre_id)`), so a same-artist row in another genre cannot supply it.
- A cross-reference set that is neither subset nor superset — Backend dropping one alias *and* gaining another — stays a mismatch.
- Fold-collapse applies only to its named columns; a sibling holding a `title` never launders a content divergence.

**Measured effect** on the 2026-08-13 prod pair: `field_mismatches` **131 → 28**, with the 103 reappearing under `normalizations` as `call_letters.fold_collapsed` 33, `artist_call_number.fold_collapsed` 59, `cross_reference_names.cardinality_gain` 11. Nothing else moved.

**Residual after this step: 28**, and none of it is a modelling gap — it is data that needs repairing:

- 11 U+FFFD replacement chars stored in Backend where MySQL holds the real character ([Backend-Service#2152](https://github.com/WXYC/Backend-Service/issues/2152)); lossy, so it needs a re-import while tubafrenzy is still reachable.
- 15 rows of post-import content divergence (`format` 7, `alternate_artist_name` 8) — insert-only ETL has no update path in either direction.
- 2 genuine title differences.

So `clean` now turns on those 28 plus `extra_unexplained` 115 ([Backend-Service#2108](https://github.com/WXYC/Backend-Service/issues/2108)'s delete), both of which are data work with owners, rather than on a definition that could never be satisfied.

**Known cost, stated plainly.** `cross_reference_names` no longer gates on cardinality in either direction. That is a property of what `LIBRARY_SELECT_SQL` can see, not a concession — but the counts stay reported per class, so a spike is still visible in `normalizations` even though it cannot block the release.
