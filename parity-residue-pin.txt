# artifact to diff against. Stating that plainly here is better than a pin
# that looks like it verifies provenance it does not.

# Backend PG (wxyc_schema). Full narrative, reproduction notes, and the

#   - residue-collapsed-599.tsv -> vendor/parity-residue/ledger.json
#     (converted). This is the frozen enumeration Part 2's Rule B cannot

# access described in residue-ledger.md's "Reproducing" section):
#   1. Re-run the residue-ledger.md queries against live prod.
#   2. Re-derive residue-collapsed-599.tsv and residue-ledger.md the same way.
#   3. python scripts/vendor_parity_residue.py \
#        --source-dir <path-to-tubafrenzy-phase3-close-out> \
#        --measured-date <YYYY-MM-DD>
#      (defaults --out-dir to vendor/parity-residue/)
#   4. Recompute the SHA-256 of both output files and update this file.
#
# The `baselines` block inside ledger.json is NOT covered by the
# re-derivation procedure above -- it is measured and reviewed independently,
# and its own change still moves ledger_json_sha256 below. vendor_parity_residue.py

# step 3's procedure does not clobber this measurement.

#   cta_missing / cta_extra -- measured 2026-08-13 against the live pair
#     (tubafrenzy MySQL wxycmusic via the Kattare tunnel; Backend prod PG
#     wxyc_schema, replaying getCompilationTrackExportRows' five INNER JOINs
#     from apps/backend/services/catalog-export.service.ts:360-377).
#     140,617 mysql rows / 2,586 releases vs 144,778 backend rows / 2,576.
#
#     These are a CEILING, not a target (the `clean` term is `<=`). Which
#     direction each number moves as the residue is repaired is NOT obvious
#     -- see the note below the decomposition. What they currently hold:
#
#       cta_missing 2701 = 869 rows in 10 mysql-only releases, every one of
#         them a collapsed_mysql_ids id below (so they are already this
#         ledger's own expected residue, arriving as CTA rows rather than
#         library rows) + 56 mojibake originals + 1,776 other.
#       cta_extra 6862 = 4,879 rows where Backend holds BOTH a byte-clean
#         copy and a double-encoded (CP1252 mojibake) copy of the same track,
#         across 780 releases, + 1,983 other. This is BS#1996's cohort
#         (5,084 mojibake rows here; that issue counted 5,310) and it is
#         still OPEN, so these are NOT remediation leftovers. The id ordering
#         says the opposite: in 638 of the 768 affected releases the mojibake
#         block sits ENTIRELY ABOVE the clean rows (0 releases the other way,
#         130 interleaved), so the corrupted rows were inserted LATER. The
#         mysql side is corrupted today -- 5,147 of its CTA rows read as
#         double-encoded -- so tubafrenzy's text was mangled at some point
#         and the insert-only importer re-imported it as NEW rows alongside
#         the pre-corruption clean ones. Nothing collapsed them: the two
#         strings differ, and no unique constraint spans the pair (a dup
#         check on (library_id, artist_name, track_title) reports zero).
#
#     Which way this resolves changes the number, so do not assume it only
#     falls. Backend's mysql-matching copies are the CORRUPTED ones, so the
#     4,879 extra are its clean rows: deleting Backend's corrupted duplicates
#     alone would convert them to cta_missing rather than removing the drift.
#     Repairing tubafrenzy's source is what actually collapses this class.
#     Re-measure and reset the ceiling once either lands -- but never raise a
#     number merely to make a red soak day pass, which inverts the gate.
#
#     The net (+4,161 backend rows) reconciles the two prior measurements

#     row-count surplus, while the 2026-08-12 run's 2,771/6,932 is the
#     two-directional MULTISET split of that same net (6,932 - 2,771 = 4,161).
#     Neither was wrong; they measure different things.
