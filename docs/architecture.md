# Architecture

## Pipeline Steps

1. **Download** Discogs monthly data dumps (XML) from https://discogs-data-dumps.s3.us-west-2.amazonaws.com/index.html
2. **(Optional, standalone) Enrich** `library_artists.txt` with WXYC cross-references (via `wxyc-enrich-library-artists` CLI from wxyc-catalog). Only useful when the operator wants the converter's artist-only filter (`--library-artists`); the pair-wise path on `--library-db` skips this step.
3. **Convert and filter** XML to CSV using [discogs-xml-converter](https://github.com/WXYC/discogs-xml-converter) (Rust binary). Accepts a single XML file or a directory containing releases.xml, artists.xml, and labels.xml. The converter applies one of two release filters inside its streaming scanner so disk only ever holds the kept rows: `--library-artists library_artists.txt` for the artist-only filter (~4M kept), or `--library-db library.db` for the pair-wise (artist, title) filter (~50K kept; what the monthly rebuild uses so the import step fits on Railway-sized destination DBs without overflowing `COPY release_artist`, see #128). Pair-wise normalization is diacritic-insensitive on both sides; known false negatives are compound-artist library entries like "Duke Ellington & John Coltrane" whose Discogs releases split into separate `release_artist` rows. When artists.xml is present, alias-enhanced filtering is enabled automatically. When labels.xml is present, `label_hierarchy.csv` is produced for sublabel-aware dedup.
4. **Create schema** (`schema/create_database.sql`) and **functions** (`schema/create_functions.sql`), then **SET UNLOGGED** on all tables to skip WAL writes during bulk import
5. **Import** filtered CSVs into PostgreSQL (`scripts/import_csv.py`)
6. **Create indexes** including accent-insensitive trigram GIN indexes (`schema/create_indexes.sql`)
7. **Deduplicate** by (master_id, format) (`scripts/dedup_releases.py`) -- partitions by master_id and normalized format so different formats (CD, Vinyl, etc.) of the same album survive dedup independently. Within each partition, prefers label match (with sublabel resolution via `--label-hierarchy`), then US releases, then most tracks, then lowest ID
8. **Prune or Copy-to** -- one of:
    - `--prune`: delete non-matching releases in place (~89% data reduction, 3 GB -> 340 MB)
    - `--copy-to`/`--target-db-url`: copy matched releases to a separate database, preserving the full import
9. **Derive `va_release`** (`scripts/derive_va_release.py`, #344) -- re-derive the VA-compilation lookup table now that dedup/prune have finalized release ids. `id` / `title` / `norm_title = lower(title)` plus a GIN trigram index on `norm_title`, selected from `release` ⋈ `release_artist` main credits matching the canonical Discogs Various artist (`artist_id = 194`, or the literal name `'Various'` for API-fetched rows whose `artist_id` is NULL). Consumed by library-metadata-lookup's compilation-matching scripts (`match_compilations.py`, `canonicalize_compilations.py`, and through them the `lml_cache.compilation_track_location` recall-index build). This is **derived data with snapshot semantics**: LOGGED (crash recovery must not empty it), no FK to `release` (so it stays out of the LOGGED/UNLOGGED flip lists and the truncate lists — protected by omission, refreshed only by re-derivation), and rebuilt atomically (DROP + CREATE TABLE AS + index in one transaction, with a bounded `lock_timeout`). Gated like prune (skipped when no `library.db` is provided — an unpruned multi-million-row cache would pay minutes deriving a table nothing reads) and **soft-fail**: a transient derive failure must not discard a non-resumable multi-hour rebuild, so the step logs a warning, best-effort-drops the stale pre-rebuild table (absent is honest and the next daily sync self-heals; stale ids would silently mismatch), and the build continues. The pipeline invocation passes `--floor 0`: post-rebuild, the pre-existing table's ids are stale, so an honest empty derivation beats the floor guard's rollback. The daily `sync-library.sh` re-derivation uses the floor guard — semantics and the `VA_RELEASE_FLOOR` knob are documented canonically in [`automation.md`](automation.md).
10. **Vacuum** to reclaim disk space (`VACUUM FULL`)
11. **SET LOGGED** to restore WAL durability for consumers

`scripts/run_pipeline.py` supports two modes:
- `--xml` mode: runs steps 3-11 (convert+filter, database build through SET LOGGED). `--xml` accepts a single file or a directory. Step 2 (enrich) is no longer part of the orchestrator — operators who want the artist-only filter run `wxyc-enrich-library-artists` separately and pass the result via `--library-artists`.
- `--csv-dir` mode: runs steps 4-11 (database build from pre-filtered CSVs)

Both modes support `--target-db-url` (deprecated, see below) to copy matched releases to a separate database instead of pruning in place, and `--resume` (csv-dir only) to skip already-completed steps. `--keep-csv` (xml mode only) writes converted CSVs to a persistent directory instead of a temp dir, so they survive pipeline failures.

## Concurrent-Rebuild Guard (Advisory Lock)

Before any of the steps above run — before step 4's schema DDL, before step 1's XML conversion even starts spawning subprocesses — `scripts/run_pipeline.py::main()` acquires a **session-level PostgreSQL advisory lock** (`pg_try_advisory_lock`, key `354001`, registered in this repo's `CLAUDE.md` "Advisory lock keys" table) on the destination cache database. This is a hard precondition of the pipeline, not an optional safety net: `main()` opens one dedicated `psycopg` connection for the lock and holds it for the entire process lifetime (see `lib/rebuild_lock.py`).

**Why session-level, not transaction-level:** the rebuild spans many transactions across many subprocess forks (`dedup_releases.py`, `import_csv.py`, `derive_va_release.py`, ...). A `pg_advisory_xact_lock` would release the instant any one of those transactions committed, well before the rebuild is done. `pg_try_advisory_lock` is held on the parent's dedicated connection for the whole run, independent of the child processes' own transactions.

**Why it must be acquired before the first fork:** advisory locks are cooperative — they only block other sessions that explicitly check the same key. A lock held by `run_pipeline.py`'s parent process does not block any SQL run by a child subprocess, because each child opens its own fresh connection. The guard only functions as a mutex if the check happens exactly once, at the earliest possible point in `main()`, strictly before `--generate-library-db`'s `wxyc-export-to-sqlite` fork and before either build-path dispatcher (`_run_xml_pipeline` / `_run_database_build`).

**Non-blocking, "bow out immediately" semantics:** `pg_try_advisory_lock` returns at once regardless of contention — a second rebuild instance never queues up behind a multi-hour rebuild. When the lock is already held, `main()` logs a warning and exits with a **distinct, non-zero, non-one exit code** (`REBUILD_LOCK_BOWED_OUT_EXIT_CODE = 75`, `lib/rebuild_lock.py`) rather than `sys.exit(0)`. `scripts/rebuild-cache.sh` checks for that exact code and reports a bow-out to Slack instead of falling through to the drift watchdog and posting a false "rebuilt successfully" — see that script's own comments for the full false-positive trap this avoids (incident #352).

Two details of that exit path are load-bearing and easy to get wrong:

- **The Python side uses `exit_bowed_out()` (`os._exit`), not `sys.exit`.** A `SystemExit` swallowed by a logging plugin — which this repo has already seen once, in the Sentry-enabled run behind #180 — would let `main()` return normally and the process exit 0, which is precisely the false "rebuilt successfully" this whole branch exists to prevent.
- **The bash side captures the code with `|| PIPELINE_EXIT_CODE=$?`, never with `set +e` bracketing.** `set +e` suppresses errexit but *not* the `ERR` trap: bash runs an `ERR` trap for any failing simple command regardless of errexit state. Bracketing the call therefore lets the trap fire first, post `:warning: failed at line N (exit 75)`, and exit 75 — leaving the entire bow-out branch as dead code. A command on the left of `||` is one of the documented cases where the trap *is* suppressed. `tests/unit/test_rebuild_cache_lock_bowout.py` executes that region under a real bash rather than only reading it, because a text-only test cannot tell the two shapes apart.

The manual-dispatch `rebuild-cache.yml` workflow is a third consumer of the sentinel. It has no bow-out reporting surface, so it kills the backgrounded `curl` (otherwise parked forever in `open()` on a FIFO whose reader never arrives, hanging the job until its 350-minute timeout) and propagates 75 as a plain failure. Red is the safe direction there; the EC2 script is where a bow-out is reported as a bow-out.

**Crash safety:** there is no explicit heartbeat or TTL. `release_rebuild_lock()` issues an explicit `pg_advisory_unlock` on every clean exit path, but a hard crash (SIGKILL, EC2 instance termination, OOM kill) skips that entirely — PostgreSQL releases every session-level advisory lock it is holding as soon as it detects that backend's connection has dropped, so a prior crashed run can never wedge the next monthly tick.

**Idle-connection safety:** the lock connection issues two statements hours apart and is otherwise idle for the whole rebuild, and `DATABASE_URL_DISCOGS` reaches Railway through their public TCP proxy. Measured against the live cache PG (17.10) on 2026-08-14: `idle_session_timeout = 0` and `idle_in_transaction_session_timeout = 0`, so the *server* never reaps the session — but `tcp_keepalives_idle = 7200s` means it would not notice a dead peer for two hours either. That leaves the proxy hop as the risk: a silent drop keeps the key held long after the client is gone, and a reset frees it mid-rebuild, silently disarming the guard. `lib/rebuild_lock.py` therefore sets client-side keepalives (30s idle / 10s interval / 5 probes) plus `connect_timeout`, applying each only when the caller's DSN does not already pin it. Because acquiring the lock is now the pipeline's first contact with Postgres — earlier than `wait_for_postgres`'s backoff loop — the connect is also retried up to three times on `OperationalError`; a *refusal* is never retried, since that is the guard working as intended.

**Scope:** session advisory locks are per-database, not cluster-wide — a lock held against the discogs-cache database does not contend with an unrelated key taken against a different database on the same Postgres server (verified empirically; see `lib/rebuild_lock.py`'s module docstring). This is exactly the property needed: two rebuild instances, in any AWS account or region, are only a hazard to each other when they point at the *same* destination database, which is the one thing every launch path — EventBridge-dispatched, manually `RunInstances`'d, run from a laptop — provably shares. It needs no IAM at all, so unlike the `Project=discogs-rebuild` tag-based EC2 guard (`scripts/rebuild-cache-bootstrap.sh`'s `abort_if_not_winning_rebuild`, #311), it cannot be silently disarmed by account/stack drift. **Both guards run** — this one does not replace #311, it backstops it; #311 still catches most collisions earlier and more cheaply (before the converter is even built), while this lock is the one that cannot be turned off by a missing IAM grant.

## Cache database CLI convention

discogs-etl follows the shared cache-builder CLI convention defined in `wxyc-etl::cli` (Rust) and mirrored here in Python:

| Flag / env | Status | Notes |
|---|---|---|
| `--database-url` | canonical | PostgreSQL URL for the cache database. |
| `DATABASE_URL_DISCOGS` | canonical | Service-specific env fallback; preferred over `DATABASE_URL`. |
| `DATABASE_URL` | deprecated fallback | Still works; emits a stderr warning that `DATABASE_URL_DISCOGS` is preferred. |
| `--target-db-url` | deprecated | Still functional but emits a stderr warning. The cache convention is consolidating on a single `--database-url`. |

Resolution order for `--database-url`: explicit flag > `DATABASE_URL_DISCOGS` > `DATABASE_URL` (deprecated) > `postgresql://localhost:5432/discogs`.

Step 1 (download) is always manual.

## master_id Column Lifecycle

The `release` table includes a `master_id` column populated during import (links a release to its Discogs "master" — the conceptual album, distinct from any specific pressing/edition). It is used during dedup (`PARTITION BY master_id, format` in `ensure_dedup_ids`) and persists through the dedup copy-swap so consumers can group editions of the same album. NULL is allowed (singles, demos, and obscure pressings often lack a master).

The dedup `CREATE TABLE new_release AS SELECT ... FROM release` SELECT list at `scripts/dedup_releases.py` (`DEDUP_TABLES` module constant) must include `master_id` for the column to survive the swap. Tests in `tests/integration/test_dedup.py::TestDedupCopySwapPreservesMasterId` pin this — they import `DEDUP_TABLES` from the production module rather than mirroring it, so the test cannot drift from production.

The `country` column behaves the same way — listed in the dedup SELECT and therefore permanent.

## artwork_checked_at Column Lifecycle

The `release` table includes an `artwork_checked_at timestamptz` column (nullable, no default) added by alembic [0008](https://github.com/WXYC/discogs-etl/issues/239). It distinguishes the two states `artwork_url IS NULL` can mean:

- **Never asked** (`artwork_checked_at IS NULL`): the bulk loader / converter never had artwork data for this row; LML has not looked it up yet either. The row falls through to a Discogs API call on the next LML lookup.
- **Asked, genuinely no image** (`artwork_checked_at IS NOT NULL` AND `artwork_url IS NULL`): LML hit the Discogs API and the release legitimately has no cover. Treated as a cache hit by LML's predicate — no further API calls.

The bulk loader (`import_csv.py:import_artwork`) leaves the column NULL on every row it writes. LML's runtime path stamps `artwork_checked_at = NOW()` in `write_release` whenever the cache is back-filled from a live Discogs API response — see [WXYC/library-metadata-lookup#423](https://github.com/WXYC/library-metadata-lookup/issues/423) for the predicate change that makes the column load-bearing.

The column survives the dedup + prune-copy-swap paths via the SELECT lists in `scripts/dedup_releases.py:DEDUP_TABLES`, `scripts/verify_cache.py:PRUNE_COPY_TABLES`, and `scripts/verify_cache.py:COPY_TABLE_SPEC` — same convention as `master_id`. Regression pins at `tests/integration/test_dedup.py::TestDedupCopySwapPreservesMasterId::test_artwork_checked_at_column_persists_after_copy_swap` and `tests/integration/test_verify_cache_columns.py::TestPruneCopyTablesCoversSchema::test_release_keeps_artwork_checked_at` prevent silent drops on future SELECT-list edits.

Partial index `release_artwork_null_idx ON release (id) WHERE artwork_url IS NULL AND artwork_checked_at IS NULL` covers the never-asked tail for [WXYC/library-metadata-lookup#221](https://github.com/WXYC/library-metadata-lookup/issues/221)'s top-up drain — without the index that scan would seq-scan the full `release` table (~82K rows in prod as of 2026-05-29).

## Artwork Preservation Across Rebuilds

The monthly rebuild is incremental by default: `release.artwork_url` and `release.artwork_checked_at` that LML's runtime back-patched between rebuilds (see [WXYC/library-metadata-lookup#423](https://github.com/WXYC/library-metadata-lookup/issues/423)) survive the next rebuild. The plumbing is two structural changes (per [#242](https://github.com/WXYC/discogs-etl/issues/242)):

1. `schema/create_database.sql` is `CREATE TABLE IF NOT EXISTS`-only — safe to apply against a populated DB. The destructive `DROP TABLE … CASCADE` block moved to `schema/drop_core_tables.sql`, invoked only by `--fresh-rebuild`.
2. `scripts/import_csv.py:import_release_via_upsert` reloads `release` via staging-table COPY + UPSERT with `artwork_url` + `artwork_checked_at` excluded from the SET list. Releases that fall out of the new dump are pruned via `DELETE … WHERE id NOT IN staging`; FK `ON DELETE CASCADE` removes their child rows. Child tables of `release` (`release_artist` + siblings, plus `cache_metadata`) are TRUNCATEd before re-COPY so duplicates don't accumulate.
3. `scripts/import_csv.py:import_artwork` also stamps `artwork_checked_at = now()` whenever it sets `artwork_url` from the dump — matches the semantics LML's runtime `write_release` applies (LML#423) so freshly-imported rows aren't treated as "never asked" on the first lookup.

**Reload invariant (discogs-etl#298)**: because the children are TRUNCATEd up front (step 2) and reloaded across several later steps, a run that aborts in that window leaves `release` full but the children empty — a state a naive row-count check reads as healthy. `scripts/run_pipeline.py` brackets the reload with a coverage check (`MIN_CHILD_COVERAGE_RATIO`, `evaluate_reload_invariant`): a **preflight** warning before the truncate if a prior abort left the cache degraded, and a **strict post-reload gate** before `report_sizes` that raises if `release` is populated but `release_track` / `release_artist` fall below the floor. Recovery: [`plan-298-empty-child-index-recovery.md`](plan-298-empty-child-index-recovery.md).

Semantics matrix for `scripts/run_pipeline.py`:

| Flag | Schema | Data | LML back-patches |
| --- | --- | --- | --- |
| (default) | preserved (`CREATE TABLE IF NOT EXISTS` no-ops) | upserted; children TRUNCATE+re-COPY | preserved |
| `--truncate-existing` | preserved | wiped via `TRUNCATE CACHE_TABLES_TO_TRUNCATE_BASE` | wiped (re-COPY into empty tables) |
| `--fresh-rebuild` | dropped + recreated via `drop_core_tables.sql` | wiped via `DROP CASCADE` | wiped |

**Dead-URL edge case the issue calls out**: if a release's image is taken down on Discogs between rebuilds, `release_image.csv` omits the row, the `import_artwork` UPDATE skips the release, and the prior LML-back-patched URL is preserved (potentially a dead URL). LML's runtime path will eventually 404 on the URL and re-fetch, back-patching with the new state. Strictly better than today's "wipe to NULL → serve placeholder" behavior.

**Plan**: [`WXYC/wiki/plans/discogs-etl-242-rebuild-coalesce.md`](https://github.com/WXYC/wiki/blob/main/plans/discogs-etl-242-rebuild-coalesce.md) (PR [wiki#75](https://github.com/WXYC/wiki/pull/75)). Regression coverage: `tests/integration/test_import.py::TestImportArtworkPreservation` (the 5-case acceptance grid), `tests/integration/test_rebuild_idempotent.py` (--truncate-existing + --fresh-rebuild semantics), `tests/integration/test_schema.py::TestSchemaIdempotenceDriftGuards` (drift guards on the schema split).

## format Column Lifecycle

The `format` column stores the normalized format category (Vinyl, CD, Cassette, 7", Digital). Unlike `master_id`, `format` persists after dedup and is available to consumers. During import, raw Discogs format strings are normalized via `lib/format_normalization.py` (e.g., "2xLP" → "Vinyl", "CD-R" → "CD"). During dedup, releases are partitioned by `(master_id, format)`, so a CD and Vinyl pressing of the same album both survive. During verify/prune, format-aware matching ensures only releases whose format matches the library's are kept (for exact artist+title matches). NULL format on either side is treated as "match anything" for backward compatibility.

## Library Release Overrides (lml_cache.library_release_override)

LML's `lml_cache.library_release_override` table pins WXYC library items to specific Discogs `release_id`s (column `discogs_release_id`). Some pinned releases fall outside the library-artist scope the monthly rebuild filters to, and two pipeline seams actively evict them whenever they happen to be present: dedup (step 7) keeps only one release per `(master_id, format)`, and prune (step 8) deletes any release whose fuzzy `(artist, title)` match fails. See [discogs-etl#327](https://github.com/WXYC/discogs-etl/issues/327).

**Mechanism**: `scripts/run_pipeline.py::write_keep_release_ids` reads the override table once per pipeline run (read-only -- degrades to an empty allowlist file only when the table/schema is genuinely absent, i.e. `UndefinedTable`/`InvalidSchemaName`, which is every DB today; a column typo or missing grant propagates and aborts the rebuild) and writes a newline-separated `release_id` allowlist file. That file's path is threaded via `--keep-release-ids <FILE>` into every `dedup_releases.py` invocation and every `verify_cache.py` invocation (`--prune`, `--copy-to`, and the post-import `--prune` path). Omitting the flag (or passing an empty/missing file) is a no-op -- byte-identical to pre-#327 behavior; this is why a standalone/manual run of either script outside the orchestrator applies no exemption.

- **Dedup** (`dedup_releases.py::ensure_dedup_ids(..., keep_ids_loaded=True)`): the exemption is baked into the `dedup_delete_ids` CTAS query itself, wrapping the unmodified `ROW_NUMBER()` ranking as an inner subquery and excluding pinned ids only at the outer level -- so ranking (and every sibling's `rn`) is unaffected; only the pinned row's delete-list membership changes. When `--keep-release-ids` is supplied, any pre-existing `dedup_delete_ids` is force-recreated (`DROP TABLE IF EXISTS` before the reuse-check) so a stale table from a prior non-exempting run can't silently skip the exemption. Hard-errors if the flag is explicitly passed but the file doesn't exist (matches the existing `--library-labels`/`--label-hierarchy` precedent).
- **Prune** (`verify_cache.py::apply_release_overrides`): runs immediately after `classify_all_releases`, unioning override ids into `report.keep_ids` and subtracting them from `report.prune_ids` -- before the `--prune`/`--copy-to`/dry-run dispatch, so all three modes are protected identically. Tolerates a missing/omitted file (matches the existing `--mappings-file` precedent).
- **Staging-prune** (`import_csv.py`) and **masters** (`import_masters`) need no changes: `import_csv.py` has no artist-based keep/drop filtering of its own on `release`/`release_artist` rows, and masters scope derives from `SELECT DISTINCT master_id FROM release`.

This transport is also designed to serve a future `discogs-xml-converter` (Rust) `--keep-release-ids` consumer -- the piece that would actually get an out-of-scope release *into* `release.csv` in the first place -- but that cross-repo change is not wired up yet. Until it (or a manual backfill) populates out-of-scope releases, this mechanism is correct and tested but inert in production: there's nothing yet in `release` outside library-artist scope for it to protect.

**One-time backfill** ([discogs-etl#329](https://github.com/WXYC/discogs-etl/issues/329)): the converter allowlist above is a going-forward fix; it does not retroactively populate releases already missing from a live cache. `scripts/query_missing_override_release_ids.py` / `scripts/check_override_parity.py` (both built on the shared query definitions in `lib/library_release_overrides.py`) regenerate the missing-ids list and verify parity for a one-time additive seed via `scripts/seed_cache_from_clone.py`. Runbook: [`docs/lml-override-backfill-runbook.md`](lml-override-backfill-runbook.md).

## Scratch Table Namespacing (dedup / prune working tables)

`dedup_releases.py` (step 7) and `verify_cache.py --prune` (step 8) both build intermediate copy-and-swap state in unqualified `public`-schema tables before renaming it into place: `dedup_delete_ids`, `keep_release_ids`, `_keep_ids`, and the `new_release*` family (`new_release`, `new_release_artist`, `new_release_label`, `new_release_genre`, `new_release_style`, `new_release_track`, `new_release_track_artist`, `new_cache_metadata`). Before [discogs-etl#356](https://github.com/WXYC/discogs-etl/issues/356) these names were global and shared by every invocation against a given database. On 2026-08-04 two concurrent rebuilds collided on them: both computed `dedup_delete_ids` identically, then one run's `DROP TABLE IF EXISTS dedup_delete_ids` deleted the other's mid-flight working set, and the survivor's copy-and-swap read from a `release` table a peer had already renamed out from under it -- 27,163 releases marked "keep" had no row left to copy ([discogs-etl#352](https://github.com/WXYC/discogs-etl/issues/352)).

**Namespacing scheme**: every scratch table name gets a random per-invocation suffix from `lib.scratch_namespace.new_scratch_suffix()` (`secrets.token_hex(4)`, 32 bits of entropy) appended via `lib.scratch_namespace.scratch_name(base, suffix)` (`f"{base}_{suffix}"`; empty suffix returns `base` unchanged). `dedup_releases.py::main()` and `verify_cache.py::prune_releases_copy_swap()` each mint one suffix at the top of their own run and thread it through every scratch-table call for that invocation. This is **per-invocation, not per-rebuild-run**: `dedup_releases.py` and `verify_cache.py` are independent `subprocess` calls from `run_pipeline.py` (each already mints its own `run_id` for the JSON logger -- see [`observability.md`](observability.md) -- because nothing threads a parent process's id into them), so getting one-schema-per-*run* would mean adding a `--run-id` flag to both scripts and every `subprocess` call site. That's out of scope: collision-safety only requires that two invocations never mint the *same* suffix, which a fresh random one per invocation already guarantees. The tradeoff, taken deliberately: a single logical rebuild's dedup step and prune step (and a manually re-run dedup after a crash) no longer share one `pg_stat_activity`-greppable, debuggable name -- each mints its own, and a stale table from a killed run can no longer be recognized by name alone as "the same logical run's leftover."

Scratch tables stay unqualified names in `public`, not a per-invocation schema. A per-schema `new_release` would need an extra `ALTER TABLE ... SET SCHEMA public` step before the existing three-statement swap (`ALTER TABLE ... RENAME TO`, used by both the copy-swap and the swap-in, cannot cross schemas) -- building under a scratch *name* in `public` avoids that extra step entirely.

**Four tables stay unnamespaced, for two different reasons.** `wxyc_label_pref` and `release_label_match` are genuinely off the monthly path: they are created only when `--library-labels` is passed, which `run_pipeline.py` derives solely from `--catalog-source`/`--catalog-db-url`, and `scripts/rebuild-cache.sh` passes neither. `label_hierarchy` and `release_track_count` are a different case and are **on** the monthly path -- `run_pipeline.py` auto-detects `label_hierarchy.csv` from the converter's output and forwards it as `--label-hierarchy`, and `import_csv.py` creates `release_track_count` on every rebuild. They stay unnamespaced because per-invocation suffixing structurally cannot cover them: both are *cross-subprocess handoff* tables, written by one script (`import_csv.py`, or an earlier dedup step) and read by another (`dedup_releases.py`), and the two processes have no shared identifier to derive a common suffix from -- the same missing-`run_id` constraint that made per-invocation suffixing the chosen scope in the first place. A concurrent peer's `DROP TABLE IF EXISTS release_track_count` can therefore still break or silently alter a run's dedup ranking (`_track_count_table_exists` falls back to counting `release_track` live, which yields a *different* `ORDER BY`). That residual window is out of scope for #356 and is only closable by the advisory lock (#354), which is the only mechanism that can serialize across subprocess boundaries.

**Crash safety, and the cleanup obligation suffixing creates.** Per-invocation suffixing removes a property the old global names quietly had: because every invocation created the *same literal names* and preceded each create with `DROP TABLE IF EXISTS`, a run that died left tables the *next* run reclaimed for free. Under suffixing no future invocation ever mints the same suffix, so nothing reclaims them by name, and an orphaned `new_release_<suffix>` is a full copy of the release table sitting in `public` indefinitely. Cleanup is therefore now an obligation of the invocation that created the tables, discharged in two layers:

1. **During the build phase -- PostgreSQL's own rollback.** `dedup_releases.build_dedup_scratch_tables()` and `verify_cache._prune_build_scratch_tables()` each run their entire build -- computing `dedup_delete_ids`/`_keep_ids` and copying every `new_X` table -- inside ONE non-autocommit transaction on a dedicated connection, committing only once everything for that invocation is built. A killed process (or a `pg_terminate_backend`'d connection) at any point in this phase leaves zero residue: PostgreSQL rolls the whole transaction back the instant it detects the connection is gone. This is the phase the `pg`-marked residue tests in `tests/integration/test_scratch_namespacing_concurrency.py` pin.
2. **After that COMMIT -- explicit cleanup on the failure path.** From the commit onward the tables are durable and rollback-on-disconnect no longer covers them. `dedup_releases.main()` wraps steps 3-5 (FK drops, swap, constraint/index build) so that any exception drops this invocation's scratch tables via `lib.scratch_namespace.drop_scratch_tables()` before re-raising; `verify_cache.prune_releases_copy_swap()` does the same around `_prune_copy_swap_tables()` + `_prune_add_base_constraints_and_indexes()`. This matters most on the prune side, where `_prune_add_base_constraints_and_indexes` is the only thing that drops `_keep_ids` and does not run at all if the swap raises first.

**Known residual gap**: a `SIGKILL` (or host loss) *after* the build transaction commits still orphans that invocation's tables, because no Python-level handler runs. There is deliberately no startup sweeper for orphaned `new_*_<suffix>` tables, and adding a naive one would be actively dangerous: after its own commit a *live* invocation's scratch tables are indistinguishable, by table state alone, from a dead run's leftovers, so a sweeper that guessed wrong would drop a healthy peer's working set -- reintroducing exactly the 2026-08-04 failure mode. Distinguishing the two requires session-liveness tracking that belongs with the advisory lock (#354). Until then, orphans from a hard kill are reclaimed manually.

The swap step itself (`swap_tables()` / the `RENAME`s in `_prune_copy_swap_tables()`) operates on already-committed state and is a separate concern from the build wrap -- see the advisory-lock note below.

**Relationship to the advisory lock (forward-looking)**: this ticket makes a namespace collision impossible; it does not make two full concurrent rebuilds against the same database safe. The sibling ticket [discogs-etl#354](https://github.com/WXYC/discogs-etl/issues/354) proposes a `pg_advisory_xact_lock` (see this repo's `CLAUDE.md` "Advisory lock keys" registry for the allocation convention) serializing the whole dedup/prune cycle; no such lock exists in this pipeline's Python today. Once it lands, the swap step -- `swap_tables()` in `dedup_releases.py` and the `RENAME`-triplet in `verify_cache.py::_prune_copy_swap_tables()`, both of which mutate the *live* `release`/`release_artist`/etc. tables and are not protected by scratch-table namespacing -- must run inside that lock's critical section, alongside the assertion work tracked by the sibling copy-swap ticket. Note the two swaps do not currently have the same atomicity: the prune swap runs its three statements as one transaction (`add_constraint_safely` with a statement list and `lock_tables`), while `dedup_releases.swap_tables()` runs on `main()`'s `autocommit=True` connection, so its `RENAME old→bak` / `RENAME new→old` / `DROP bak CASCADE` are three separate transactions with a window in which the live table does not exist. Namespacing does not narrow that window; only the lock can. Namespacing (#356) and the advisory lock (#354) are complementary, not redundant: the lock prevents the collision outright; namespacing means a collision that happens anyway (a lock bypassed by a code path that forgets to take it, or an operator running the pipeline manually outside the lock) destroys at most one invocation's own scratch state instead of a peer's.

### Library Catalog (library.db)

`library.db` is a SQLite export of the WXYC library catalog, generated by the `wxyc-export-to-sqlite` CLI from the wxyc-catalog package. The default source is tubafrenzy's MySQL database on Kattare (via SSH), but Backend-Service's PostgreSQL database can be used instead via `--catalog-source backend-service --catalog-db-url <url>`. The `--catalog-source` flag is supported by `run_pipeline.py` and the wxyc-catalog CLI tools. The legacy `--wxyc-db-url` flag is an alias for `--catalog-source tubafrenzy --catalog-db-url <url>`.

`library.db` is used as input throughout the pipeline:

1. **`library_artists.txt`** -- Generated from `library.db` by `wxyc-enrich-library-artists` (wxyc-catalog CLI), one artist name per line, used by `discogs-xml-converter --library-artists` for filtering
2. **KEEP/PRUNE classification** -- `scripts/verify_cache.py` uses `library.db` to match cached releases against the WXYC catalog

`scripts/sync-library.sh` orchestrates the daily sync: query Kattare MySQL via the MariaDB `mysql` CLI (required for MySQL 4.1's old-format password hashes), convert TSV to SQLite via `scripts/tsv_to_sqlite.py`, enrich with streaming links from `streaming_availability.db` (a [GitHub Release artifact](https://github.com/WXYC/library-metadata-lookup/releases/tag/streaming-data-v1) in library-metadata-lookup, refreshed weekly), then upload to LML staging and production via `POST /admin/upload-library-db`. The Discogs pipeline can also generate `library.db` inline via `--generate-library-db` using the wxyc-catalog CLI.

### Catalog parity producers (tubafrenzy turndown)

Retiring the `wxycmusic` MySQL means moving that daily build's catalog source to Backend-Service — but only once a Backend-sourced `library.db` is proven field-equivalent to the MySQL-sourced one, or every downstream consumer (LML search, streaming checks, compilation matching, dj-site catalog, iOS metadata) silently regresses. `scripts/catalog_parity_diff.py` builds both sides and diffs them:

```bash
PARITY_DIR=$(mktemp -d)              # fresh each run: both --*-db paths must not already exist
export LIBRARY_DB_PASSWORD=...       # never in the DSN -- see below
export BACKEND_CATALOG_EMAIL=catalog-parity@wxyc.invalid
export BACKEND_CATALOG_PASSWORD=...  # the service account's password; the harness mints per run

python scripts/catalog_parity_diff.py \
    --mysql-source "mysql://$LIBRARY_DB_USER@127.0.0.1:13306/$LIBRARY_DB_NAME" \
    --mysql-db "$PARITY_DIR/mysql.db" \
    --backend-source https://api.wxyc.org \
    --backend-db "$PARITY_DIR/backend.db" \
    --json
```

Neither new #370 flag appears above, and both omissions are deliberate. `--residue-ledger` already defaults to the vendored ledger, so naming it here would only substitute a cwd-relative path for a module-relative one that cannot break. `--fail-on-drift` is left off because this block is the *interactive* invocation, where an operator reads the counts — the exit-4 verdict belongs to the scheduled soak, not to a hand run. See the two bullets below.

- **MySQL side** reproduces the daily build exactly: the same `mysql -B -N` CLI invocation (a Python driver cannot authenticate against tubafrenzy's MySQL), the same two SELECTs — a unit test lifts every `-e "SELECT ..."` out of `sync-library.sh` and asserts set equality with the harness's copies, because a baseline built from a *different* query would make parity measure the harness rather than the migration — and the same TSV parser. The password comes from **`LIBRARY_DB_PASSWORD`** and reaches the CLI via `MYSQL_PWD`: embedding it in the DSN would put it in *this* process's argv (visible to `ps`, echoed by `set -x` and by GitHub Actions command traces) and would need percent-encoding for `/`, `#`, `?`, `%`. A missing `COMPILATION_TRACK_ARTIST` table is tolerated, as in the daily sync.
- **Backend side** is decision D3 / Option B ([wiki#89](https://github.com/WXYC/wiki/issues/89), 2026-08-03): the gzipped-NDJSON `GET /library/catalog` + `GET /library/catalog/compilation-tracks` exports ([Backend-Service#1965](https://github.com/WXYC/Backend-Service/issues/1965)) over HTTPS with a service-account bearer token (needs `catalog:read`). Option B was chosen over a direct-Postgres producer precisely so no prod-DB credential has to live in GitHub Actions; plain `http://` to anything but a loopback address is refused, and so is any cross-origin redirect — urllib copies `Authorization` into a redirected request, so a 302 from a proxy or hijacked DNS would otherwise replay the token to a host nobody named.
- **`--residue-ledger`** is omitted above because it already defaults to `vendor/parity-residue/ledger.json`, resolved relative to `catalog_parity_diff.py`'s own location rather than the invoking shell's `cwd` — so the invocation works from any directory, which passing the path literally would undo (a relative path exits 3 from anywhere but the repo root). Pass `--residue-ledger none` to run without one; row-level expected/unexplained classification and `clean` are then unavailable, and `clean` reports `null` in `--json` (printed as `None` on the human surface).
- **`--fail-on-drift`** turns a non-clean verdict into exit 4, which is what a scheduled soak workflow would gate on — see "Unwired secrets (catalog parity)" in [`docs/automation.md`](automation.md) for why no such workflow exists yet. It is safe to add to the invocation above **as of the 2026-08-13 CTA baseline** (plan step 6): `baselines.cta_missing` / `baselines.cta_extra` are populated, so `clean` is no longer structurally `false`. Before that measurement both were `null` and the CTA term was `false` *even for two byte-identical `library.db` files*, which made the flag exit 4 on every run — if you are reading a checkout whose `vendor/parity-residue/ledger.json` still carries nulls, that older caveat applies again.

#### Minting and rotating the parity service account (#365)

The bearer above **cannot be a stored secret**. `requirePermissions` accepts only a JWKS-verified JWT, and better-auth issues those with a 15-minute expiry (its default, which Backend-Service does not override) — so what CI stores is the service account's *password*, and `catalog_parity_diff.py` mints a token per run from `BACKEND_CATALOG_EMAIL` + `BACKEND_CATALOG_PASSWORD`. `BACKEND_CATALOG_TOKEN` still works for a one-off run with a JWT already in hand: it takes precedence, and if it turns out to be stale the run falls back to minting from the credential pair rather than failing on a 15-minute-old token it could replace. Two optional overrides exist for non-prod: `BACKEND_AUTH_URL` (defaults to `<--backend-source>/auth`) and `BACKEND_AUTH_ORIGIN` (defaults to `https://dj.wxyc.org`, which must be one of the auth server's `BETTER_AUTH_TRUSTED_ORIGINS` — better-auth's CSRF guard rejects an origin-less sign-in).

A run outlives its 15-minute token, so the harness refreshes — and how it refreshes is shaped by the two rate limiters in front of `/auth/sign-in` (the express one, 10 per 15 min; better-auth's own, 3 per 10s). It caches the *session* and refreshes by re-exchanging at `/auth/token`, which is exempt from the express limiter; only an exchange that itself 401s (a dead session) costs a second sign-in, and there are at most two sign-ins per run. The two budgets are separate — spending the sign-in allowance must never disable refreshing against a session that still works. A 429 whose retry hint exceeds 10s is **not** waited out: the run fails quoting the hint, because retrying into a 15-minute window is a guaranteed second refusal and the operator wants the real number. Nor is a 429 that carries no usable hint at all — both limiters here send one, so a bare 429 came from something else in front of them whose window can't be guessed. If either happens, check whether something else is signing in as the service account.

**Mint** (one-time, needs an admin session on `api.wxyc.org/auth`):

**`scripts/mint-parity-service-account.sh` does all of this**, and is the path to prefer — it reads the admin password without echo, revokes the admin session from a `trap` on the way out, and exercises the new credential (sign-in + JWT exchange) before reporting success, which is what proves the org `member` row landed:

```bash
./scripts/mint-parity-service-account.sh --admin-email you@example.org
```

The steps below are what it does, kept here because a runbook that only says "run the script" is useless the day the script is the thing that's broken. Every password reaches `curl` on **stdin**, never in argv — same reason `LIBRARY_DB_PASSWORD` goes through `MYSQL_PWD` above. `-d "{...$PASSWORD...}"` would put it in a command line that `ps` shows to every user on the box and that `set -x` echoes into the scrollback.

```bash
# 1. Admin sign-in -> session token.
SESSION=$(jq -n --arg e "$ADMIN_EMAIL" --arg p "$ADMIN_PASSWORD" '{email:$e,password:$p}' \
    | curl -sS -X POST https://api.wxyc.org/auth/sign-in/email \
        -H 'Content-Type: application/json' -H 'Origin: https://dj.wxyc.org' \
        --data-binary @- | jq -r .token)

# 2. Create the principal with a password, no email, no setup token.
#    Keep USER_ID: rotation and revocation both need it.
PASSWORD=$(python3 -c 'import secrets; print(secrets.token_urlsafe(48))')
USER_ID=$(jq -n --arg p "$PASSWORD" \
    '{email:"catalog-parity@wxyc.invalid",name:"Catalog Parity",password:$p,data:{emailVerified:true}}' \
    | curl -sS -X POST https://api.wxyc.org/auth/admin/create-user \
        -H "Authorization: Bearer $SESSION" -H 'Content-Type: application/json' \
        -H 'Origin: https://dj.wxyc.org' --data-binary @- | jq -r .user.id)

# 3. Store it where CI reads it.
gh secret set BACKEND_CATALOG_EMAIL --repo WXYC/discogs-etl --body catalog-parity@wxyc.invalid
printf %s "$PASSWORD" | gh secret set BACKEND_CATALOG_PASSWORD --repo WXYC/discogs-etl --body-file -
```

If `USER_ID` was not captured at mint time, recover it with `POST /auth/admin/list-users` (`{"searchField":"email","searchValue":"catalog-parity@wxyc.invalid"}`) rather than guessing.

**Rotate**: repeat step 2 as `POST /auth/admin/set-user-password` with `{"userId":"$USER_ID","newPassword":"..."}`, then **revoke the old sessions** — `POST /auth/admin/revoke-user-sessions` with `{"userId":"$USER_ID"}` — then step 3. The revocation is not optional bookkeeping: `set-user-password` revokes nothing, and Backend-Service pins `session.expiresIn` to **365 days** (`shared/authentication/src/auth.definition.ts`), so a rotation without it orphans the stored secret while leaving every previously-minted session able to keep exchanging for `catalog:read` JWTs for a year. The harness signs out the session it mints (`_TokenSource.close`, in a `finally`), so in the normal case there is nothing left to revoke — this covers the runs that died before they could.

Nothing else consumes these secrets, so rotation is atomic from the soak's point of view as long as it doesn't land mid-run.

Three things about that procedure are load-bearing:

- **`admin/create-user`, not `admin/provision-user`.** The org's own wrapper refuses a caller-supplied password and emails an account-setup link whose token is valid for **7 days** (`shared/authentication/src/account-setup-token.ts`) — the length of the soak. Setting the password afterwards does not revoke it, so anyone who could read that mailbox could reset the account mid-soak. better-auth's admin endpoint takes the password directly and mints no token. Backend-Service handles this path explicitly: a `hooks.after` branch auto-verifies the email (BS#1118) and the `user.create.after` hook inserts the org `member` row, which is where the `catalog:read` permission actually comes from.
- **`member` is the least-privileged role that carries `catalog:read`.** Every WXYC role has it; `member` is the floor. The residual grants are `bin:read/write` (its own DJ bin) and `flowsheet:read` — no catalog write, no flowsheet write. A truly catalog-read-only role would need a new entry in the shared `WXYCRole` union across three repos.
- **No `role` field in the create-user body.** That field is better-auth's *global* admin role (`user.role`), not the org role — leaving it at the default keeps the account outside the admin plugin entirely.
- **`@wxyc.invalid`, deliberately not `@wxyc.org`.** The address is an identifier, not a mailbox: `.invalid` is reserved by [RFC 2606](https://www.rfc-editor.org/rfc/rfc2606#section-2) and can never be delegated in the global DNS, so no mail can reach it *and no future change can make it reachable*. That last clause is the point — an `@wxyc.org` address needs no mailbox today, but anyone who later adds a catch-all silently hands whoever reads it the ability to run `forget-password` against an account holding the whole catalog. Nothing in the mint path sends mail (`admin/create-user` mints no token and the body sets `emailVerified`), and rotation is admin-driven, so the account never needs to receive anything. One consequence to know: a `forget-password` submitted for this address makes SES attempt delivery to a domain that cannot resolve, which is a hard bounce against the org's sender reputation. Rotate through `admin/set-user-password`; never through the reset flow.

If the account ever needs revoking: rotate the password **and** revoke the sessions (both above — the password alone leaves year-long sessions live), and ban the user if the compromise is active. The JWT payload carries `banned` and `requirePermissions` 403s on it, so a ban takes effect within one 15-minute token turnover; it is the only one of the three that also invalidates a JWT already in flight.

Properties worth knowing before reading a parity report:

- **`legacy_release_id` becomes `library.db`'s `id`.** Backend's serial `library.id` collides with the tubafrenzy id space (max 72,276), so the producer emits `legacy_release_id` ([Backend-Service#1963](https://github.com/WXYC/Backend-Service/issues/1963) mints these from 1,000,000 up). A row without one fails the build rather than writing a null id.
- **The two exports are two requests, not one transaction.** They form a consistent snapshot only while the shared `library_watermark` holds still across both; the producer re-fetches the pair when the watermark moves (or when a compilation track references a release the catalog body doesn't contain) and fails after three attempts rather than diffing a torn snapshot and reporting the tear as drift. `Last-Modified` is an HTTP-date, so two watermarks inside the same second compare equal — a write landing in that window can leave a single spurious `extra_in_backend`, which self-heals on the next run.
- **Nulls arrive as `''`.** `sync-library.sh` wraps `alternate_artist_name` / `album_artist` / `cross_reference_names` in `IFNULL(<col>, '')`, so prod holds `''` and the Backend build matches. `cross_reference_names` crosses the wire as an **array** and is `' | '`-joined here — the delimiter never travels, because nothing stops an artist name from containing a pipe. A scalar where the array belongs is rejected, not joined: `' | '.join("Stereolab")` would write one phantom alias per letter.
- **A producer failure never masquerades as drift.** An empty catalog export, a row missing an api.yaml-`required` field, and a non-integer `legacy_release_id` all abort with exit 3 rather than producing a database that reports the whole catalog as `missing_in_backend`. Every producer failure is exit 3, including ones that aren't the harness's own (`mysql` not on `PATH`, a malformed DSN, an unwritable output directory).
- **Row-level divergence splits into expected vs. unexplained, and only the latter blocks `clean`** ([#370](https://github.com/WXYC/discogs-etl/issues/370)). `missing_in_backend`/`extra_in_backend` count every id-level difference, including known residue: a duplicate tubafrenzy row Backend's ETL correctly collapsed onto one release, a BS#1963-minted id with no tubafrenzy counterpart, a row Backend's ETL deliberately skipped (a `db_only` genre, an unparseable format, an empty artist name or album title). Two rule classes need no ledger entry at all (a minted id, a row-derivable skip reason); the one thing that genuinely needs an enumerated ledger entry is the 599 `findExistingRelease` duplicate-collapse ids, vendored in `vendor/parity-residue/ledger.json`. `clean` is `True` only when every unexplained count is zero, `field_mismatches` is all-zero, and CTA drift sits within the ledger's baseline; `False` on any of those failing; and `None` — absent, not failed — when no ledger was supplied (`--residue-ledger none`). `normalizations` (column → class → count) is reported alongside `clean` but never gates it.

- **Some divergence is explained by a row other than the one being compared** ([#346](https://github.com/WXYC/discogs-etl/issues/346) step 9). tubafrenzy's unit of artist identity is the `LIBRARY_CODE` row, and 295 presentation names have more than one (596 code rows, 542 carrying releases). Backend's unit is the `artists` row, matched by `fold_artist_name`, so those collapse into one row holding a single `code_letters` and a single `artist_genre_code` per genre. Every release filed under the *other* code then reads as a field mismatch against a value that is entirely legitimate — just not that release's. `call_letters` and `artist_call_number` therefore resolve against the folded artist's whole mysql row group and report `fold_collapsed`; `cross_reference_names` collapses the same way but as a set union, so it needs no group context and reports `cardinality_gain`. **None of the three is blanket acceptance**: the value has to be one the mysql side itself supplies (`artist_call_number` additionally scoped to the row's own genre, because `ensureGenreArtistCrossref` keys on `(artist_id, genre_id)`), and a cross-reference set that is neither subset nor superset stays a mismatch. Measured on prod 2026-08-13: 103 rows, taking `field_mismatches` from 131 to 28.
- **`cross_reference_names` can no longer gate on cardinality in either direction, and that is a property of the query, not a concession.** `LIBRARY_CODE_CROSS_REFERENCE` is joined per *code*, but `LIBRARY_SELECT_SQL` only reaches codes that carry a release — so a duplicate code with zero releases is invisible here while Backend still folds it in. Both directions are reported per class, so a spike is still visible in `normalizations`; it just does not block `clean`.

Both producers refuse to write to a path that already exists: the harness only ever builds scratch copies and must never be able to clobber a real `library.db`. Each builds into a hidden `.partial` file beside its target and renames it into place only on success, so a failed run leaves nothing behind for the next day's run to refuse — but the two `--*-db` paths still have to be fresh, hence the `mktemp -d` above.

#### U+FFFD pair capture (`--capture-fffd-cta-pairs`, WXYC/Backend-Service#2152)

A one-off sibling mode, not part of the daily-sync producer story above: `--capture-fffd-cta-pairs PATH` pairs every Backend `compilation_track_artist` row holding a literal U+FFFD REPLACEMENT CHARACTER against its tubafrenzy MySQL truth, and writes the result as JSON to `PATH` (`-` for stdout). It exists because the 2026-08-13 prod parity run ([#346](https://github.com/WXYC/discogs-etl/issues/346) step 8a) found 14 such values and no laptop can capture them: `BACKEND_CATALOG_EMAIL`/`BACKEND_CATALOG_PASSWORD` are repo secrets, and the Homebrew MySQL 9.x client segfaults against tubafrenzy's MySQL 5.1 (`mariadb-client` is what works — see [#378](https://github.com/WXYC/discogs-etl/issues/378)). CI is the only place both sides are reachable at once; this mode rides that.

**To run it, dispatch `catalog-parity.yml` with `capture_fffd_cta_pairs` checked** ([#382](https://github.com/WXYC/discogs-etl/issues/382)) — Actions → Catalog Parity Soak → Run workflow. The capture is an opt-in step of the soak's own job rather than a workflow of its own, because that job is the one place the service-account secrets and a working `mariadb-client` already coexist, and because it can then reuse the `library.db` the soak just built (`--mysql-db`, no `--mysql-source`) instead of taking a second full-catalog export against Kattare's 5-connection pool. It runs only when the parity harness itself exited `0` or `4` — the two codes that mean the export completed, so the SQLite is whole; pairing against a half-built catalog would report MySQL rows as `zero_candidates`, a wrong answer shaped exactly like a real finding. The result uploads as `catalog-parity-fffd-exit<code>-<run_id>-<run_attempt>` and `scripts/fffd_capture_summary.py` renders the verdict. See [`automation.md`](automation.md#capturing-ufffd-cta-pairs-382).

The invocation below is the manual equivalent, for a laptop that has a Kattare tunnel and the credentials:

```bash
PARITY_DIR=$(mktemp -d)
export LIBRARY_DB_PASSWORD=...
export BACKEND_CATALOG_EMAIL=catalog-parity@wxyc.invalid
export BACKEND_CATALOG_PASSWORD=...

python scripts/catalog_parity_diff.py \
    --capture-fffd-cta-pairs "$PARITY_DIR/fffd-pairs.json" \
    --mysql-source "mysql://$LIBRARY_DB_USER@127.0.0.1:13306/$LIBRARY_DB_NAME" \
    --mysql-db "$PARITY_DIR/mysql.db" \
    --backend-source https://api.wxyc.org
```

`--backend-source` is required (not `--backend-db`): the bulk `GET /library/catalog/compilation-tracks` export deliberately omits both the CTA row id and `track_position` (api.yaml's `CatalogCompilationTrackRow` docstring says shipping them "would break parity" with library.db's 3-column CTA table), so this mode makes one further call per affected release — `GET /library/{id}/compilation-tracks` (`CompilationTrack`, BS#1964), keyed on Backend's own serial id rather than `legacy_release_id` — to recover `track_position`. `track_position` is not itself corrupted by this bug (it carries no non-ASCII content), so Backend's live value is trustworthy without a MySQL cross-check; the pairing rule below never touches it.

**The pairing rule** (`lib/fffd_pair_capture.py`, no I/O, unit-tested in isolation) covers two layered corruption shapes, tried in order, and accepts a candidate that satisfies either one:

1. **Substitution-only** (what the module originally assumed): the corruption is one-byte-in-one-codepoint-out, so character length is preserved (`La Bête` → `La B<U+FFFD>te`, both 7 characters) and every non-U+FFFD position is untouched. A MySQL row is a candidate for a corrupt column only if it has the same character length and agrees at every non-U+FFFD position.
2. **Forward-simulated** (discogs-etl#386 — the shape all 14 of the first production dispatch's rows turned out to be, not shape 1). Two things are different about these rows. First, the U+FFFD run is one placeholder **per destroyed byte**, not per destroyed character, so a single lost character surfaces as a run of **2 or 3 adjacent U+FFFD** and the character count is no longer preserved — shape 1's length rule can never match them. Second, most of them had *also* been run through the WXYC/Backend-Service#1996 double-encoding class before the damage landed: MySQL's correct UTF-8 bytes misread once as MySQL's `latin1` (`Décalé` → `DÃ©calÃ©`), inflating the character count again. Undoing any of that is impossible, not merely awkward: on row 53042, splitting the corrupt value on U+FFFD and un-mojibaking the fragment before the gap (`"DÃ".encode("cp1252")` → a lone UTF-8 lead byte `0xC3` with no continuation) raises `UnicodeDecodeError` by construction. The rule therefore **forward-simulates** instead — it never decodes the corrupt value, it only encodes the clean candidate and compares. Each MySQL candidate is simulated three ways (`_forward_simulations`: the value itself, its MySQL-`latin1` double-encoding, its ISO-8859-1 one) and accepted only if one of them reproduces the observed Backend string exactly, with each U+FFFD run standing for **exactly that many UTF-8 bytes** of the simulation (`_fffd_gap_match`).

   The byte width is the load-bearing constraint, not a detail: prefix byte length is strictly increasing in character count, so a run of width *N* consumes a *uniquely determined* span of the simulation, and a run that would end mid-character fails outright. Without it a run at index 0 (rows 11615 `artist_name`, 53478) or at the end (row 56717) degenerates into a suffix- or prefix-only filter that a wrong candidate can clear alone — resolving the row with no `multiple_candidates` to catch it. Worked example: MySQL's `Décalé Chinois` simulates to `DÃ©calÃ© Chinois`; the observed `DÃ<U+FFFD><U+FFFD>calÃ© Chinois` matches because the 2-wide run at index 2 stands for exactly the 2 UTF-8 bytes of `©`, and every character on either side agrees exactly. The identity simulation is in the set because row 11704 (`Huldresl<U+FFFD><U+FFFD>tten = The Wood Nymph Tune`) is not double-encoded at all — it is clean UTF-8 that lost both bytes of its `å`.

The same OR applies to the **anchor column** (the one with no U+FFFD, previously required to match byte-for-byte): it can itself be *clean* double-encoded mojibake, with no data loss and hence no U+FFFD at all, so byte equality alone would wrongly disqualify it — row 8844's anchor is `Wanda SÃ¡` on Backend against MySQL's clean `Wanda Sá`. The anchor rule is therefore "equals one of the MySQL value's simulations". There is no gap in that comparison — the anchor has no U+FFFD by definition — so it is still exact, character for character, and a different track on the same release still fails it. The producer codec is MySQL's `latin1`, i.e. **windows-1252**, which maps the five bytes Python's strict `cp1252` leaves unassigned (`0x81`, `0x8D`, `0x8F`, `0x90`, `0x9D`) to the C1 controls `U+0081`…`U+009D` rather than raising; the live artifact carries those codepoints (rows 49848, 58487, 59002, 59194, 67454), and neither of Python's stock codecs can spell them — strict `cp1252` raises, and ISO-8859-1 renders the whole `0x80`-`0x9F` range as controls, contradicting the `‚`/`ƒ`/`„`/`Œ` those same rows also carry.

Exactly one candidate resolves the row under either shape; zero or more than one reports it **unresolved**, with the candidates considered — never a guess, and never an accent-stripped or visually-similar substitute (this is exactly the population — `Csillagrablók`, `Bête`, `µ-Ziq`, `Décalé Chinois` — where such a guess is a wrong answer). Two candidates whose simulations differ only *inside* a U+FFFD gap correctly report `multiple_candidates` rather than either being picked. A row corrupt in both `artist_name` and `track_title` resolves as one row carrying both true values, never two. `current_artist_name` / `current_track_title` on every emitted pair stay byte-identical to Backend's raw corrupt value — never the decoded or forward-simulated form — because Backend-Service's repair SQL (`bs_replacement_char_cta.sql`) joins on those columns matching the live corrupt row; a cleaned value there silently zeroes out the join.

**What the rule still cannot decide, and the consumer must not forget.** The gap stands for bytes the corruption destroyed, and nothing in the Backend value can reconstruct them. Every `D<U+00C0…U+00FF>calé Chinois` simulates into row 53042's observed value. When two such values are both present in the candidate set the row reports `multiple_candidates` and emits nothing; when only a *wrong* one is present and the true value is absent from MySQL, the row resolves to it, silently and uniquely. A resolved pair is therefore a proof that the candidate is *consistent with the observed damage*, not a proof that it is the original — which is why the resolved set is a repair proposal for human review before BS#2152's `UPDATE`, not an auto-apply artifact.

**MySQL is the source of truth only while it is itself clean.** Position-wise agreement (shape 1) and gap-matching (shape 2) both treat the Backend placeholder as absorbing unknown content, so a MySQL value carrying a U+FFFD at or near that same position could agree trivially and be emitted as `true_*` — writing the corruption into the repair while reporting success. Such a candidate is rejected, and when it is the only one the row reports `corrupt_candidates` rather than `zero_candidates`: the two need different remedies, since a byte tubafrenzy has also lost is not recoverable by the re-import BS#2152 describes. Byte-identical candidates are collapsed before counting — duplicate CTA rows are ordinary in this catalog, and two identical rows carry one answer — but the comparison is byte-exact, so two candidates differing in the corrupt column still report `multiple_candidates`.

**Exit codes** follow the harness's own taxonomy: `0` every corrupt row resolved (including the vacuous zero-corrupt-rows case), `4` the run was fine but at least one row is unresolved, `3` a source or write failure, `2` a usage error. The `4` matters because this mode exists to produce a specific set of pairs — "ran fine, captured nothing usable" is as actionable as a crash and, at exit 0, just as invisible. `PATH`'s parent directory is validated *before* any fetching (a path error after the exports would throw away a report that only CI can retake), and a write that fails anyway dumps the JSON to stdout rather than losing it.

The JSON output is `{"resolved": [...], "unresolved": [...], "sql_values": "..."}`. Each resolved entry carries `legacy_release_id`, `track_position`, the corrupt and true value for each column (`null` on a column that was not corrupt), and `true_*_codepoints` — every non-ASCII character in the true value named individually as `{"index", "char", "codepoint"}` (e.g. `"U+00B5"`), so a reviewer can confirm `µ` MICRO SIGN was captured rather than `μ` GREEK SMALL LETTER MU without trusting a font. `sql_values` renders every resolved row as `pending_cta_repair` VALUES tuples in Backend-Service's `scripts/audit/bs_replacement_char_cta.sql` column order (`legacy_release_id, track_position, current_artist_name, current_track_title, true_artist_name, true_track_title`) — paste it in place of that block's placeholder row.
